## 1. 배경 및 문제 정의

### 1.1 배경
러닝 인구는 늘었지만, 대다수의 러너는 **혼자 달리다 3개월 안에 그만둔다.** 기존 앱은 두 갈래로 갈린다.

- **기록 정밀도형** (Garmin Connect, Apple 피트니스): 데이터는 정확하지만 혼자 보는 대시보드에 그친다. 달릴 이유를 만들어주지 못한다.
- **소셜 커뮤니티형** (Strava, Nike Run Club): 피드·팔로우·클럽 중심이라 **관계 맺기가 전제**된다. 아는 사람이 없으면 아무것도 작동하지 않는다.

즉, **혼자여도 성립하는 경쟁**이라는 축이 비어 있다. 대다수 러너는 크루에 가입할 생각이 없고, 남의 피드를 보고 싶어하지도 않는다. 그저 **자기 노력이 눈에 보이는 형태로 쌓이고, 남들 사이에서 자기 위치를 알고 싶어할 뿐이다.**

### 1.2 핵심 문제
1. 혼자 달리면 동기가 유지되지 않는다. → **지속률 문제**
2. 노력의 결과가 등급·순위·보상 같은 **비교 가능하고 축적되는 형태**로 남지 않는다. → **피드백 문제**
3. 경쟁하려면 인간관계(크루 가입, 친구 추가)를 먼저 맺어야 한다. → **진입 마찰 문제**
4. 달리기의 보상이 순전히 내재적이라, 동기가 꺾이면 회복 수단이 없다. → **보상 부재 문제**

### 1.3 우리의 가설
> 러너에게 **아무도 몰라도 즉시 참여되는 경쟁 구조**와 **영구히 쌓이는 뱃지**, 그리고 **실제 가치로 교환되는 포인트**를 주면, 관계 형성 없이도 경쟁 동기가 작동하고 4주차 리텐션이 유의미하게 개선된다.

### 1.4 보상 구조의 4중 시간축

이 제품의 핵심 설계는 **서로 다른 시간축의 보상을 겹쳐 쌓는 것**이다.

| 보상 | 시간축 | 평가 방식 | 심리적 역할 |
|------|--------|----------|------------|
| **주간 랭킹** | 1주 (리셋) | 상대평가 (티어 내) | 지금 당장 뛸 이유 — **긴박감** |
| **티어** | 3개월 (리셋) | **절대평가** (누적 거리 기준) | 시즌 전체를 관통하는 목표 — **성취감** |
| **뱃지 · 레벨** | 영구 (누적) | 절대평가 | 그만두지 못할 이유 — **매몰 자산** |
| **포인트** | 적립 후 소진 | — | 동기가 꺾였을 때의 안전망 — **외재적 보상** |

🔵 **설계 원칙**: 네 축은 서로를 대체하지 않는다.
- 주간 랭킹만 있으면 → 장기 목표가 없어 매주 소모된다
- 티어만 있으면 → 3개월은 너무 길어 첫 달에 긴박감이 없다
- 뱃지만 있으면 → 타인과의 비교가 없어 경쟁이 성립하지 않는다
- 포인트만 있으면 → 러닝 앱이 아니라 리워드 앱이 된다

## 2. 제품 비전 및 포지셔닝

### 2.1 한 문장 정의
> **Runnit은 혼자 달려도 경쟁이 되는 러닝 앱이다.** 아는 사람 없이 시작해서, 뛴 만큼 티어가 오르고 순위가 오른다.

### 2.2 포지셔닝
| 축 | Strava | Nike Run Club | Garmin Connect | 캐시워크 | **Runnit** |
|----|--------|---------------|----------------|---------|-----------|
| 중심 경험 | 소셜 피드 | 코칭 프로그램 | 기록 분석 | 걸음 리워드 | **티어 + 랭킹 + 뱃지** |
| 관계 형성 필요 | 필수 | 불필요 | 불필요 | 불필요 | **불필요** |
| 경쟁 요소 | 클럽·세그먼트 | 약함 | 없음 | 없음 | **핵심** |
| 성장 가시화 | 약함 | 중간 | 데이터만 | 없음 | **티어로 명시** |
| 외재적 보상 | 없음 | 없음 | 없음 | 강함 | **있음 (Phase 4)** |
| 기록 신뢰도 | 높음 | 높음 | 매우 높음 | 낮음 | **높음 (서버 검증)** |

🔵 **경쟁 지형에서의 위치**: Strava는 "관계"가 있어야 작동하고, 캐시워크는 "보상"만 있고 경쟁·기록 품질이 없다. Runnit은 **정확한 기록 위에 등급·경쟁·보상을 동시에** 올린다.

### 2.3 하지 않을 것 (Non-Goals)
- **소셜 피드 / 팔로우 / DM** — 관계 맺기를 전제하지 않는 것이 우리의 차별점이다
- **크루를 중심에 둔 설계** — 크루에서 활용될 수는 있으나, 크루를 위한 앱이 아니다
- 코칭·훈련 프로그램 생성 (v1 범위 밖)
- 사이클·수영 등 러닝 외 종목
- 자체 웨어러블 하드웨어
- 포인트의 현금 환급 — 상품 교환만 지원 (§8.7 규제 사유)

## 3. 타깃 사용자

### 3.1 주 페르소나 — "정체된 솔로 러너" (P1, 최우선)
- 20~30대, 주 2~3회 5~10km. 러닝 경력 6개월~3년.
- **혼자 달린다. 앞으로도 혼자 달릴 생각이다.** 크루는 부담스럽거나 관심 없음.
- 기존 앱으로 기록은 남기지만 **"그래서 내가 어느 정도인지"** 를 모른다.
- **원하는 것**: 내 실력의 객관적 등급, 비슷한 사람들 사이에서의 위치, 노력의 흔적.

### 3.2 부 페르소나 — "보상 반응형 러너" (P2)
- 20~40대, 주 1~2회 또는 재시작을 반복. 캐시워크·토스 만보기 등 리워드 앱 사용 경험 있음.
- 러닝 자체의 즐거움만으로는 지속되지 않음. **눈에 보이는 이득**이 필요.
- **원하는 것**: 달린 만큼 쌓이는 포인트, 실제로 쓸 수 있는 리워드.
- 🔵 포인트(Phase 4)가 이 층을 끌어오고, 티어·뱃지가 이들을 P1으로 전환시키는 것이 목표.

### 3.3 3차 페르소나 — "기업 담당자" (P3, Phase 5)
- 사내 건강관리/복지 담당. 임직원 챌린지를 운영.
- **원하는 것**: 참여율 리포트, 부서 대항 리더보드. → BRD의 B2B 수익 모델 대상.
- 🔵 이 페르소나만이 그룹 기능을 필요로 한다. 즉 **그룹 기능은 B2C 요구가 아니라 B2B 요구**다. 이것이 크루를 P2로 내리는 근거다.

## 4. 핵심 사용자 시나리오

### 4.1 첫 달리기 (신규 사용자) — 관계 형성 없이 60초 내 진입
1. 앱 설치 → 소셜 로그인 → 닉네임·체중·주간 목표 설정 (3화면)
2. 위치 권한 요청 (왜 필요한지 설명 화면 선행)
3. **[START]** → 실시간 화면: 거리 / 페이스 / 시간 / 지도 경로
4. 종료 → 요약 화면에서 **보상 동시 노출**:
   - 🏅 "첫 러닝" 뱃지 획득 연출
   - 🥉 "브론즈 티어 · 실버까지 24.8km" — 시즌 목표 제시
   - 📊 "브론즈 티어 내 128위" — **친구 추가 없이 이미 경쟁 중**
5. 다음 목표 제시: "3km 더 뛰면 주간 랭킹 100위 진입"

🔵 **핵심**: 4번 단계에서 사용자는 아무도 팔로우하지 않았는데 이미 등급과 순위를 받았다. 이것이 Strava와의 결정적 차이다.

### 4.2 이중 경쟁 루프 (핵심 리텐션 구조)

```
┌─ 시즌 루프 (3개월, 절대평가) ───────────────────────────┐
│                                                          │
│  시즌 시작   전원 최하위 티어에서 출발                    │
│      ↓                                                   │
│  누적 거리   기준선 돌파 시 즉시 승급 연출 + 뱃지         │
│      ↓       "실버 달성! 골드까지 62km"                  │
│      ↓                                                   │
│  시즌 종료   최종 티어 확정 → 시즌 기록에 영구 보존       │
│              → 티어 달성 뱃지 지급 → 다음 시즌 리셋       │
│                                                          │
│   ┌─ 주간 루프 (1주, 상대평가) ─────────────────┐        │
│   │  월 00:00  주간 랭킹 리셋 (티어 내)          │        │
│   │      ↓                                        │        │
│   │  주중     기록 업로드 → 순위 갱신             │        │
│   │      ↓     "3계단 상승, 현재 14위"            │        │
│   │      ↓                                        │        │
│   │  금~일    "10위까지 2.1km" 푸시 → 막판 유도   │        │
│   │      ↓                                        │        │
│   │  일 23:59 주간 순위 확정 → 주간 뱃지          │        │
│   └───────────────────────────────────────────────┘        │
│                    (시즌 내 13회 반복)                     │
└──────────────────────────────────────────────────────────┘
```

🔵 **두 루프의 역할 분담이 이 제품의 뼈대입니다.**
- 주간 랭킹은 **이번 주에 뛰게** 만든다 (짧은 긴박감, 상대평가)
- 티어는 **시즌 내내 뛰게** 만든다 (긴 성취감, 절대평가 — 남과 무관하게 내 노력만큼 오름)

### 4.3 영구 루프 (뱃지·레벨)
주간 랭킹이 리셋되고 티어가 시즌마다 초기화되어도, **뱃지·레벨·누적 거리·역대 시즌 티어 기록은 영구히 남는다.** 순위에서 밀린 주에도 "누적 500km 뱃지까지 12km" 같은 장기 목표가 이탈을 막는다.

### 4.4 포인트 소진 루프 (Phase 4)
```
달리기 → 뱃지·티어·순위 달성 → 포인트 적립 → 리워드샵 교환 → 다시 달리기
                                                    ↑
                                          제휴사 노출 = 수익 (BRD)
```

## 5. 기능 요구사항

우선순위: **P0** = MVP 출시 필수 / **P1** = 출시 후 6주 내 / **P2** = 이후

### 5.1 러닝 트래킹 (P0)

| ID | 요구사항 | 우선순위 | 수용 기준 |
|----|---------|---------|----------|
| TR-01 | GPS 기반 실시간 거리·페이스·시간 측정 | P0 | 1km 실측 대비 오차 ±3% 이내 |
| TR-02 | 백그라운드 추적 (화면 꺼짐/앱 전환 시 유지) | P0 | 60분 연속 기록 시 데이터 손실 0 |
| TR-03 | 일시정지 / 재개 / 자동 일시정지 | P0 | 정지 15초 감지 시 자동 일시정지 |
| TR-04 | 지도 경로 실시간 표시 | P0 | 5초 이내 최신 위치 반영 |
| TR-05 | GPS 노이즈 스무딩 (정확도 낮은 포인트 제거) | P0 | 터널·고층 구간 비현실적 점프 제거 |
| TR-06 | 칼로리 추정 (MET 기반) | P0 | 체중·거리·페이스 반영 |
| TR-07 | 구간별(1km) 랩 기록 | P0 | 요약 화면 랩 테이블 |
| TR-08 | 오프라인 기록 → 복귀 시 자동 동기화 | P0 | 네트워크 없이 기록 후 100% 업로드 |
| TR-09 | 음성 안내 (1km마다 페이스·티어 진행률) | P1 | 티어 안내가 차별 요소 |
| TR-10 | 실내 러닝(트레드밀) 수동 입력 | P1 | 티어·랭킹 반영 여부는 §8.3 |
| TR-11 | 러닝 시작 전 목표 설정(거리 또는 시간) + 진행 중 목표 대비 진행률·달성 알림 | P1 | 목표 도달 시 1회 알림, 진행률 바 0~100% |

🔵 **TR-11 구현 메모**: 목표는 현재 **화면 로컬 상태**로만 구현되어 있다
(`lib/features/tracking/presentation/tracking_page.dart`의 `_RunGoal`). 서버에
저장되지 않고 앱을 벗어나면 초기화되며, 트래킹 엔진(`RunTrackingService`)에도
전달되지 않는다 — 자동 종료 없음, 화면 레이어에서 `activeRunProvider`의 실시간
거리/시간과 비교해 진행률·달성 알림만 그린다. 서버 영속화·요약 화면 표시·목표
기반 자동 종료가 필요해지면 데이터 모델/엔진 확장이 별도로 필요하다.

### 5.3 티어 시스템 (P0) — **핵심 차별 기능 ①**

**설계 전제**: 티어는 **절대평가**다. 남이 얼마나 뛰든 무관하게, **내 시즌 누적 거리가 기준선을 넘으면 승급**한다.

🔵 **이 방식의 결정적 이점**: 사용자 수와 무관하게 작동한다. 출시 첫날 사용자가 10명이어도 티어 시스템은 정상 동작한다. (상대평가 리그였다면 매칭 인원 부족으로 붕괴)

#### 5.3.2 티어 기준선 (초안)

**확정.** 주 페르소나(주 2~3회 × 5~10km ≈ 주 15~30km, 분기 195~390km)를 기준으로 역산했습니다.

| 티어 | 시즌 누적 거리 | 도달 예상 | 설계 의도 |
|------|--------------|----------|----------|
| 🥉 **브론즈** | 0km ~ | 가입 즉시 | 전원 출발점 |
| 🥈 **실버** | 25km 이상 | 2~3주차 | **초기 이탈 방지** — 첫 승급을 빠르게 |
| 🥇 **골드** | 100km 이상 | 6~7주차 | 시즌 중반 목표 |
| 💎 **플래티넘** | 250km 이상 | 11~13주차 | **시즌 끝까지 끌고 가는 목표** |

**기준선 설계 원칙**:
1. **첫 승급은 최대한 빨리** — 2주 안에 아무 보상이 없으면 이탈한다
2. **최고 티어는 시즌 막바지에 도달** — 8주차에 만렙이면 남은 5주가 공백이 된다
3. **간격은 점증** — 25 → 100 (4배) → 250 (2.5배)

⚠️ **알려진 한계 (수용)**: 플래티넘 250km는 분기 기준 **주 평균 19km**입니다. 상위 러너는 시즌 절반에 최고 티어에 도달해 후반 목표가 사라집니다. 이들에게는 **주간 랭킹과 누적 뱃지**가 후반 동기를 담당합니다. 5번째 티어 추가는 실사용 데이터 확인 후 재검토 (v2 후보).

#### 5.4.1 티어 인원 불균형 — **수용된 트레이드오프 (확정)**

절대평가 티어이므로 인원이 균등하게 나뉘지 않습니다. **시즌 초에는 전원이 브론즈**이고, 시즌 말에는 상위 티어가 얇아집니다.

**결정: 이 불균형을 해소하지 않는다.** 서브 그룹 매칭 로직을 도입하지 않습니다.

| 판단 | 근거 |
|------|------|
| 매칭 로직 미도입 | 티어 내 서브 그룹 분할은 결국 상대평가 리그 매칭의 부활이며, 구현·운영 복잡도가 이득을 상회 |
| 불균형 자체는 무해 | 티어 **승급 판정**은 절대평가라 인원과 무관하게 정상 작동. 영향받는 것은 주간 랭킹의 *체감*뿐 |
| 시간이 해결 | 시즌이 진행되며 자연히 상위 티어로 분산됨 |

**완화책 (매칭 없이 표기 방식만으로 처리) — P0 요구사항에 반영:**

| 상황 | 완화 |
|------|------|
| 브론즈 3,000명 중 2,847위 | 절대 순위 대신 **"상위 34%"** 병기 (RK-04) |
| 순위 숫자가 체감되지 않음 | **바로 위/아래 사용자와의 격차**를 주 지표로 노출 — "0.8km만 더" (RK-04) |
| 시즌 말 플래티넘 인원 부족 | 그대로 노출. 소수 정예라는 사실 자체가 희소성 신호 |

🔵 **핵심**: 사용자가 실제로 반응하는 것은 "2,847위"가 아니라 **"0.8km만 더 뛰면 앞사람을 제친다"** 입니다. 인원이 몇 명이든 이 신호는 동일하게 작동합니다.

**랭킹 기준: 주간 누적 거리 단독 (확정)**
- 형평성은 **티어 분리**가 이미 담당한다. 랭킹까지 보정하면 이중 보정이 된다
- 복합 점수(거리+페이스+꾸준함)는 "왜 내가 3등이지?"가 불투명해져 CS를 유발한다
- 복합 점수는 P2 실험 과제로 유보 (§10.2-#13)

## 8. 핵심 정책

### 8.1 티어 판정 규칙
- **기준**: 시즌 내 누적 러닝 거리 (검증 통과 기록만 합산)
- **판정 시점**: 기록 저장 즉시 (배치 대기 없음)
- **강등**: 시즌 중 없음 (TI-08)
- **시즌 종료**: 최종 티어를 이력에 영구 기록 후 전원 브론즈로 초기화
- **기록 삭제 시**: 누적 거리 재계산 → 기준선 미달 시 **티어는 하향 조정**
- **지급된 뱃지 회수 (확정)**:

| 삭제 사유 | 티어 | 뱃지 | 포인트(Phase 4) |
|----------|------|------|----------------|
| 사용자 자발적 삭제 | 하향 | **회수하지 않음** | 회수하지 않음 |
| 부정 기록으로 판정·무효화 (§8.4) | 하향 | **회수** | **회수** |

🔵 **근거**: 정상 사용자가 실수로 지운 기록 때문에 뱃지를 뺏으면 반발이 크고, 그 손실이 얻는 정합성보다 큽니다. 반면 부정 기록은 회수하지 않으면 조작 유인이 남습니다.

### 8.2 주간 랭킹 동점 처리
동일 주간 거리일 경우:
1. 더 적은 러닝 횟수로 달성한 사람 (효율)
2. 먼저 해당 거리에 도달한 사람 (시간)
3. 총 러닝 시간이 짧은 사람 (페이스)

### 8.3 티어·랭킹 반영 대상
- **반영**: 앱 GPS 기록 / 웨어러블 동기화 기록(P1~, 별도 정책 §5.7)
- **미반영**: 수동 입력 기록, 트레드밀 기록

**트레드밀·수동 기록 처리 (확정)**

| 항목 | 처리 |
|------|------|
| 기록 저장 | ✅ 저장됨 |
| 누적 통계·히스토리 | ✅ 반영 |
| 전용 실내 뱃지 | ✅ 지급 |
| **티어 누적 거리** | ❌ 미반영 |
| **주간 랭킹** | ❌ 미반영 |

🔵 **근거**: 검증 불가능한 수동 입력이 티어에 들어가면 **티어 전체의 신뢰가 무너집니다.** 티어와 랭킹은 이 앱의 화폐이므로 검증된 기록만 받습니다. 대신 겨울철·우천 이탈은 **실내 전용 뱃지와 누적 통계 반영**으로 완충합니다 — 기록은 남고 인정도 받되, 경쟁 지표에는 들어가지 않습니다.

### 8.4 부정행위 방지 (서버 검증) — **P0 필수**

서버(Supabase Edge Function)에서 업로드 시 검증:

| 검사 | 기준 | 조치 |
|------|------|------|
| 비현실적 페이스 | 평균 3:00/km 미만 | 티어·랭킹 제외 + 플래그 |
| 순간 속도 이상 | 구간 속도 25km/h 초과 | 해당 구간 제거 후 재계산 |
| 시간 대비 거리 불일치 | 샘플 간 거리/시간 모순 | 기록 거부 |
| 중복 업로드 | 동일 시간대 중복 기록 | 병합 또는 거부 |
| GPS 샘플 부재 | 샘플 없이 거리만 존재 | 수동 기록으로 분류 (미반영) |
| 경로 비현실성 | 직선 이동·순간 이동 패턴 | 플래그 후 수동 검토 |
| 다계정 의심 | 동일 기기·동일 경로 반복 | Phase 4 포인트 적립 보류 |

**원칙**: 클라이언트 계산 값을 신뢰하지 않고 **서버에서 원본 샘플로 재계산**한다.
플래그 누적 시 랭킹 참여 제한. **이의 제기 경로 필수 제공.**

### 8.5 시즌 · 주간 경계

| 구분 | 기준 |
|------|------|
| 시즌 | **역년 분기** — 1/4/7/10월 1일 00:00 시작 (KST) |
| 주간 | KST 월요일 00:00 ~ 일요일 23:59 |
| 경계 걸침 | 러닝 **시작 시각** 기준으로 귀속 |
| 시즌 말 주간 | 시즌 종료일이 주 중간이면 해당 주간 랭킹은 단축 운영 |
| 첫 시즌 | 출시일 ~ 다음 분기 시작일까지 **단축 시즌**으로 운영 |

🔵 **역년 분기를 택한 근거**: 사용자에게 "2026 Q3 플래티넘"이 직관적이고, 티어 달성 뱃지(GM-07)의 명명이 자연스럽습니다. 출시일 기준이면 시즌 경계가 사용자마다 설명하기 어려운 날짜가 됩니다.

### 8.6 주중 승급 시 랭킹 이관 (확정)

주중에 티어가 오르면 즉시 새 티어의 주간 랭킹으로 편입되며, **그 주에 이미 쌓은 주간 누적 거리를 그대로 가지고 이동한다.**

🔵 **근거**: 초기화하면 **승급이 곧 순위 손실**이 되어, 사용자가 승급을 주말까지 미루는 왜곡된 행동을 유발합니다. 보상 구조가 서로를 방해해서는 안 됩니다.

## 11. 릴리스 로드맵 (1인 개발 기준)

**전제 (v1.3 확정)**: 범위는 유지하고 **일정을 실투입 시간 기준으로 재산정**한다.

- 투입 가능: **주 10~20시간** (본업 병행)
- 작업량 추정: **약 520시간** (전업 기준 640시간에서 AI 에이전트 활용분 약 -19% 반영)
- ⚠️ AI로 단축되는 것은 **코드 작성**뿐이다. **실기기 테스트·GPS 현장 검증·스토어 심사·디버깅·설계 판단은 단축되지 않는다.**

| Phase | 작업량 | **주 20시간** | 주 15시간 | 범위 |
|-------|-------|--------------|----------|------|
| **Phase 0** | 65h | **3주** | 4주 | 아키텍처·데이터 모델·Supabase 스키마 확정 |
| **Phase 1 (P0 전반)** | 195h | **10주** | 13주 | GPS 트래킹, 기록 저장/히스토리, 계정 |
| **Phase 2 (P0 후반)** | 160h | **8주** | 11주 | **티어 + 주간 랭킹**, 뱃지·레벨, 알림, 서버 검증, **공유 카드(HI-08·HI-10)** |
| **Phase 3** | 100h | **5주** | 7주 | 베타, 성능·배터리 최적화, 심사 대응 |
| **🚀 MVP 출시** | **520h** | **26주 (약 6개월)** | 35주 (약 8개월) | P0 전체 |
| **Phase 4** | 260h | +13주 | +17주 | 웨어러블 연동, **포인트 이코노미 + 리워드샵** (제휴 계약 선행) |
| **Phase 5** | 260h | +13주 | +17주 | 그룹/크루, B2B 기업 챌린지 콘솔 |

### 목표: **MVP 26~30주 (약 6~7개월)**

⚠️ **이 목표는 주 20시간 유지를 전제로 한다.** 주 15시간으로 떨어지면 자동으로 35주(8개월)가 된다. 투입 시간이 일정을 직접 결정하므로, **일정이 밀리는 것은 실패가 아니라 투입량의 산술적 결과**로 취급한다.

🔵 **일정을 늘리되 범위를 지킨 이유**: P0 항목은 대부분 서로 물려 있다. 티어 없이 랭킹이 성립하지 않고, 서버 검증 없이 랭킹의 신뢰가 없으며, 공유 카드 없이는 성장 수단이 없다(BRD §5.2). **잘라낼 수 있는 독립 항목이 거의 없으므로 시간으로 흡수한다.**

⚠️ **범위 유지의 대가**: 첫 검증(BRD §8.2 +4개월 게이트)이 **착수 후 약 10~12개월** 뒤로 밀린다. 이 기간 동안 시장 피드백 없이 만들게 되며, 이것이 A안의 실질적 리스크다.

🔵 **완화책 — Phase 1 종료 시점(착수 +13주)에 클로즈드 베타를 권장한다.** GPS 트래킹과 기록 저장만으로도 "거리가 정확한가, 배터리가 버티는가"라는 **가장 큰 기술 리스크는 검증 가능하다.** 티어·랭킹이 없어도 이 검증은 성립하며, 여기서 실패하면 나머지를 만들 이유가 없다.

🔵 **포인트를 Phase 4에 둔 이유**: 리워드샵에 교환할 상품이 없으면 포인트는 부채일 뿐이고, 기프티콘 제휴 협상은 **사용자 수 실적이 있어야 유리**합니다. MVP로 사용자 확보 → 그 수치로 제휴 계약 → 포인트 오픈 순서가 현실적입니다.

⚠️ **일정 리스크**: MVP 출시(16주) 후 첫 시즌은 3개월(13주)입니다. 즉 **티어 시스템의 효과를 완전히 검증하려면 출시 후 최소 3개월이 필요**합니다. 그 전에는 주간 랭킹·뱃지 지표로만 판단해야 합니다.
