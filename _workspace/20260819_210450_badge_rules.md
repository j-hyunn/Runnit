## 1. 뱃지 카탈로그

### 1.1 `criteria_type` 확정 집합 — **이 12개가 전부다**

backend는 아래를 `CHECK (criteria_type IN (...))`로 못박아도 된다. 값 추가는 gamification-designer 승인 후 마이그레이션으로만.

| `criteria_type` | 의미 | `threshold` 단위 | 비교 방향 | 값의 출처 |
|---|---|---|---|---|
| `run_count` | 정상 완료 러닝 총 횟수 | 회 | `>=` | `profiles.total_run_count` (캐시) |
| `single_run_distance_m` | 단일 러닝 최장 거리 | m | `>=` | `max(runs.distance_meters)` |
| `total_distance_m` | 누적 거리 | m | `>=` | `profiles.total_distance_meters` (캐시) |
| `total_moving_seconds` | 누적 이동 시간 | s | `>=` | `profiles.total_moving_seconds` (캐시) |
| `streak_days` | **역대 최장** 연속 러닝 일수 | 일 | `>=` | `profiles.longest_streak_days` (캐시) |
| `pace_sec_per_km_below_5k` | 5km 이상 러닝 중 최고(최소) 평균 페이스 | s/km | **`<=`** | `min(moving/(dist/1000)) WHERE distance_meters >= 5000` |
| `pace_sec_per_km_below_10k` | 10km 이상 러닝 중 최고(최소) 평균 페이스 | s/km | **`<=`** | 위와 동일, `>= 10000` |
| `single_run_elevation_gain_m` | 단일 러닝 최대 누적 상승 | m | `>=` | `max(runs.elevation_gain_meters)` |
| `total_elevation_gain_m` | 누적 상승 고도 합 | m | `>=` | `sum(coalesce(elevation_gain_meters,0))` |
| `early_run_count` | KST 05:00~06:59 시작 러닝 횟수 | 회 | `>=` | `count(*)` + KST 시각 필터 |
| `night_run_count` | KST 21:00~03:59 시작 러닝 횟수 | 회 | `>=` | `count(*)` + KST 시각 필터 |
| `challenge_completed_count` | 완주한 챌린지 수 | 개 | `>=` | `count(*) FROM challenge_participations WHERE completed_at IS NOT NULL` |

**비교 방향 규칙 (SQL 이식 시 반드시 분기):**

```
IF criteria_type LIKE 'pace_sec_per_km_below%' THEN
    earned := (current_value IS NOT NULL AND current_value <= threshold);
ELSE
    earned := (current_value >= threshold);
END IF;
```

페이스 지표만 "작을수록 좋음"이다. 이 한 줄을 빠뜨리면 **모든 사용자가 첫 러닝에 페이스 뱃지 4종을 전부 받는다** (초기값 0 또는 NULL이 threshold 이하로 판정되므로). `current_value IS NULL`(해당 거리 러닝이 없음)일 때 미획득이어야 한다는 점도 함께 강제할 것.

**집계 대상 러닝 (모든 `criteria_type` 공통):**
```sql
WHERE user_id = p_user_id
  AND status = 'completed'
  AND is_flagged = false
```
`runs_user_completed_idx (user_id, ended_at) WHERE completed AND NOT flagged`가 이 술어를 커버한다(backend §7).
`discarded`/`recording`/`paused` 및 플래그된 기록은 뱃지 판정에서 완전히 배제한다 — 랭킹·프로필 통계와 동일한 기준이라 사용자가 "랭킹엔 없는데 뱃지는 받았다"는 모순을 겪지 않는다.

**`streak_days`가 `current_streak_days`가 아니라 `longest_streak_days`인 이유:** 30일 연속을 달성한 뒤 하루 쉬면 `current`가 0으로 리셋된다. `current` 기준으로 판정하면 판정 순간을 놓친 사용자가 영원히 뱃지를 못 받는다. 이미 달성한 기록은 소멸하지 않아야 하므로 `longest`를 쓴다. **backend는 `recompute_profile_stats`가 `longest_streak_days`를 반드시 `evaluate_badges` 호출 이전에 갱신하도록 트리거 순서를 보장할 것.**

**동기부여 곡선 근거 — 왜 등간격이 아닌가**

임계값을 10/20/30km처럼 등간격으로 놓으면 초반엔 지루하고 후반엔 뱃지가 무의미해진다. 대신 두 축을 썼다.

1. **의미 있는 단위 우선** — 단일 러닝 거리는 5K/10K/하프(21.0975km)/풀(42.195km)로 잡았다. 러닝 문화에 이미 존재하는 이정표라 사용자가 목표를 스스로 이해한다. 고도 누적은 에베레스트(8,848m)를 썼다.
2. **누적형은 약 5배씩 증가** — 50 → 250 → 1,000 → 5,000km. 로그 스케일에 가까워 브론즈는 2~3주 안에, 플래티넘은 수년에 걸쳐 달성된다.

첫 러닝 한 번으로 `first_run`(50pt) + `single_5k`(5km 이상이면 60pt)를 즉시 얻는다. **첫 세션에서 최소 1개는 반드시 획득**하도록 `first_run`의 threshold를 1로 뒀다 — 첫 획득 연출이 리텐션에 가장 크게 기여하는 구간이기 때문이다.

뱃지 포인트 총합은 약 14,300pt다. §4 레벨 곡선에서 레벨 10(16,800pt)에 근접하는 값이라, "뱃지만 모아도 레벨이 오른다"와 "뱃지만으로는 상위 레벨에 못 간다"를 동시에 만족한다.

### 1.3 미충족 카테고리 — `social`

`BadgeCategory.social`에 해당하는 뱃지를 **의도적으로 0개**로 뒀다. 크루(`crews`) 테이블이 아직 정의되지 않았고(architect 문서 §3, backend §9-3), 친구 관계 테이블도 없다(backend §9-5). 판정 소스가 없는 뱃지를 시드하면 영원히 획득 불가능한 항목이 갤러리에 남는다. **크루 기능 착수 시 gamification-designer 재소집이 필요하다** (`crew_member_days`, `crew_run_together_count` 등 신규 `criteria_type` 추가 동반).

## 2. 판정 시점과 서버 재검증 원칙

### 2.1 원칙: 클라이언트는 주장할 수 없다

`GamificationRepository`(`lib/core/repositories/gamification_repository.dart`)에는 "뱃지를 부여한다" 메서드가 없다. RLS도 `user_badges` INSERT를 거부한다. **이 두 가지를 유지하는 것이 부정행위 방지의 전부다.** GPS 좌표를 조작해 시속 40km 기록을 만드는 것은 클라이언트에서 얼마든지 가능하므로, 클라이언트 판정 결과를 신뢰하는 순간 랭킹과 뱃지가 동시에 무너진다.

방어선은 이미 backend §6의 `validate_run()`이 세워뒀다. 뱃지 판정은 그 뒤에 선다:

```
러닝 upsert
  → runs_guard (BEFORE): avg_pace 재계산, validate_run() → is_flagged 확정, awarded_points 재산정
  → runs_recompute_stats (AFTER): profiles 통계 캐시 재계산 (total_*, streak, level)
  → recompute_challenge_progress (AFTER): 참가 중 챌린지 진척 갱신 + 완주 확정   [신규, §6]
  → evaluate_badges (AFTER, 마지막): 미획득 뱃지 전량 재평가                    [신규]
```

**순서가 중요하다.** `evaluate_badges`는 `profiles` 캐시(`total_distance_meters`, `longest_streak_days`, …)와 `challenge_participations.completed_at`을 읽으므로 반드시 마지막이어야 한다. 순서가 뒤집히면 마일스톤이 한 세션씩 밀려서 지급된다.

### 2.2 판정 방식: "이번 러닝으로 뭘 얻었나"가 아니라 "아직 못 받은 게 있나"

**채택: 매 러닝 업로드마다 해당 사용자의 미획득 활성 뱃지를 전량 재평가한다.**

```sql
-- evaluate_badges(p_user_id uuid, p_source_run_id uuid) 의사코드
FOR b IN
    SELECT * FROM badges
    WHERE is_active = true
      AND id NOT IN (SELECT badge_id FROM user_badges WHERE user_id = p_user_id)
LOOP
    v_current := current_value_for(p_user_id, b.criteria_type);   -- §1.1 출처 표 참조
    IF b.criteria_type LIKE 'pace_sec_per_km_below%' THEN
        v_earned := (v_current IS NOT NULL AND v_current <= b.threshold);
    ELSE
        v_earned := (v_current IS NOT NULL AND v_current >= b.threshold);
    END IF;

    IF v_earned THEN
        INSERT INTO user_badges (user_id, badge_id, earned_at, source_run_id, is_seen)
        VALUES (p_user_id, b.id, now(), p_source_run_id, false)
        ON CONFLICT (user_id, badge_id) DO NOTHING;   -- 동시성 방어

        -- 뱃지 포인트를 프로필에 가산 (INSERT가 실제로 일어났을 때만)
        IF FOUND THEN
            UPDATE profiles
               SET total_points = total_points + b.points
             WHERE id = p_user_id;
        END IF;
    END IF;
END LOOP;

-- 루프 종료 후 레벨 1회 재계산
UPDATE profiles SET level = compute_level(total_points) WHERE id = p_user_id;
```

**"세션형 vs 누적형"을 구분하지 않은 이유가 이 설계의 핵심이다.** 세션 종료 이벤트만 구독하면 여러 세션에 걸쳐 쌓이는 마일스톤형 뱃지(누적 100km, 최장 스트릭)를 구조적으로 놓친다. 반대로 전량 재평가는 두 유형을 자동으로 포섭한다 — 카탈로그가 29종, 사용자당 미획득분은 그보다 적고, 값의 대부분이 `profiles` 캐시에서 O(1)로 나오므로 러닝 1건당 비용이 무시할 만하다.

`ON CONFLICT DO NOTHING`은 오프라인 러닝이 재업로드되거나(멱등 upsert, backend §3.2) 두 기기에서 동시에 업로드될 때 뱃지가 중복 지급되는 것을 막는다. `UNIQUE (user_id, badge_id)`가 그 근거다.

### 2.3 스트릭처럼 여러 세션에 걸친 판정 — 언제 어떤 쿼리로

`streak_days`는 `profiles.longest_streak_days`를 읽는 O(1) 조회다. 실제 계산은 `recompute_profile_stats`가 이미 수행한다(backend §7의 `runs_user_completed_idx`가 "사용자별 스트릭 날짜 추출"을 커버한다고 명시됨). 계산 규약만 확정한다:

- **일자 기준은 KST(Asia/Seoul)** — 리더보드 기간 경계(backend §5.6)와 동일 타임존이어야 한다. 다르면 "랭킹은 오늘인데 스트릭은 어제"가 발생한다.
- **일자 귀속은 `started_at` 기준.** 23:50에 출발해 자정을 넘긴 러닝은 출발일에 귀속된다. `ended_at` 기준으로 하면 자정 직전 출발이 다음 날로 넘어가 사용자가 체감하는 "오늘 뛰었다"와 어긋난다.
- 하루에 여러 번 뛰어도 1일로 센다 (`DISTINCT` 날짜).
- 집계 대상은 §1.1과 동일 (`completed AND NOT flagged`).

```sql
-- longest_streak_days 계산 (gaps-and-islands)
WITH d AS (
  SELECT DISTINCT (started_at AT TIME ZONE 'Asia/Seoul')::date AS run_date
  FROM runs WHERE user_id = p_user_id AND status='completed' AND is_flagged=false
),
g AS (
  SELECT run_date, run_date - (row_number() OVER (ORDER BY run_date))::int AS grp FROM d
)
SELECT coalesce(max(cnt),0) FROM (SELECT count(*) AS cnt FROM g GROUP BY grp) s;

-- current_streak_days: 위 d에서 오늘(KST) 또는 어제부터 역방향으로 연속인 구간 길이.
-- '어제까지 연속'도 유효로 본다 — 오늘 아직 안 뛰었다고 스트릭이 끊긴 것으로 표시하면
-- 사용자가 자정 전에 뛰어도 이미 0으로 보여 동기가 꺾인다.
```

### 2.4 카탈로그 변경과 소급 적용

- **신규 뱃지 추가:** 기존 사용자는 **다음 러닝 업로드 시** 자동으로 획득한다(전량 재평가 방식의 부수 효과). 즉시 소급이 필요하면 backend가 `SELECT evaluate_badges(id, NULL) FROM profiles;`를 1회 배치 실행한다(`source_run_id = NULL` 허용 — 모델상 nullable).
- **기존 뱃지 조건 변경 금지 원칙:** 이미 획득한 사용자에게 소급 박탈이 없어야 한다. `evaluate_badges`가 미획득분만 훑으므로 threshold를 올려도 기존 획득자는 영향받지 않는다. **뱃지를 없앨 때는 DELETE가 아니라 `is_active = false`로 한다** — `user_badges`의 FK와 획득 이력이 보존된다.
- **`badges.points` 변경 시 주의:** 이미 지급된 포인트는 소급 조정하지 않는다. 조정하려면 backend가 별도 정산 배치를 짜야 한다.

### 2.5 서버 검증 실패 기록의 취급

`is_flagged = true`가 된 기록은 뱃지 판정 소스에서 빠지지만, **이미 지급된 뱃지를 회수하지 않는다.** `validate_run()`의 임계값(backend §6)은 오탐 여지가 있고(터널·고층 빌딩 구간의 GPS 점프 등), 설명 없이 뱃지를 빼앗는 것은 정상 사용자에게 가장 나쁜 경험이다. 플래그된 기록은 랭킹·통계·포인트에서만 제외되고, UI는 해당 기록에 "검증 대기" 상태를 표시한다.

> **flutter-ui-designer 협의 필요:** 현재 `RunRecord` 모델에 `isFlagged`가 없어 클라이언트가 "왜 내 기록이 랭킹에 없는지" 표시할 수 없다(backend §9-1과 동일 지적). architect 조율 항목으로 §7에 올린다.

## 3. 포인트 산식 확정

### 3.1 확정 공식

```
compute_awarded_points(
    p_status            run_status,
    p_is_flagged        boolean,
    p_distance_meters   double precision,
    p_moving_seconds    integer,
    p_elevation_gain_m  double precision   -- nullable
) RETURNS integer

-- ① 자격 검사
IF p_status <> 'completed' OR p_is_flagged THEN RETURN 0;
IF p_distance_meters IS NULL OR p_distance_meters < 500 THEN RETURN 0;

-- ② 거리 점수: 100m당 1점  (PLACEHOLDER를 그대로 계승 — 사용자가 이미 이해하기 쉬운 단위)
v_distance_pts := floor(p_distance_meters / 100.0);          -- 10km → 100pt

-- ③ 완주 보너스: 고정 20pt
v_base := 20;

-- ④ 페이스 보너스: 2km 이상 러닝에만 적용
v_pace := CASE WHEN p_distance_meters >= 2000 AND p_moving_seconds > 0
               THEN p_moving_seconds / (p_distance_meters / 1000.0)
               ELSE NULL END;                                 -- s/km
v_mult := CASE
            WHEN v_pace IS NULL  THEN 0.00
            WHEN v_pace <= 300   THEN 0.30      -- 5'00"/km 이내
            WHEN v_pace <= 360   THEN 0.20      -- 6'00"/km 이내
            WHEN v_pace <= 420   THEN 0.10      -- 7'00"/km 이내
            ELSE 0.00
          END;
v_pace_pts := floor(v_distance_pts * v_mult);

-- ⑤ 고도 보너스: 상승 10m당 1점, 최대 100pt
v_elev_pts := least(floor(coalesce(p_elevation_gain_m, 0) / 10.0), 100);

-- ⑥ 합산 + 상한
RETURN least(v_base + v_distance_pts + v_pace_pts + v_elev_pts, 1000)::integer;
```

**반영 대상:** `supabase/migrations/20260819140400_04_validation_and_stats.sql` — `compute_awarded_points()` 본문. backend §6에 "이 두 함수 본문만 교체하면 되고 호출부는 건드릴 필요 없다"고 적혀 있으므로 시그니처가 다르면 호출부(`runs_guard`)에서 인자만 맞춰주면 된다.

### 3.2 각 항의 근거

| 항 | 값 | 왜 |
|---|---|---|
| 최소 거리 500m | 미만은 0점 | GPS 노이즈로 생기는 수십 미터짜리 유령 세션에 포인트를 주지 않는다. 500m는 `validate_run`의 평균속도 검사 하한(400m)보다 살짝 높게 잡아 "검증은 통과했지만 점수는 없는" 구간을 명시적으로 만든다 |
| 완주 보너스 20pt | 고정 | 거리 비례만 두면 2km 러너는 20pt, 20km 러너는 200pt로 10배 차이가 난다. 고정 보너스가 짧게 자주 뛰는 사용자의 이탈을 막는다 |
| 거리 100m당 1pt | 선형 | 사용자가 암산할 수 있는 유일한 규칙("10km = 100점"). 여기에 곡선을 넣으면 아무도 이해하지 못한다 |
| 페이스 보너스 최대 +30% | 곱셈 | 덧셈 보너스로 하면 짧고 빠른 러닝이 유리해져 어뷰징 유인이 생긴다. 거리 점수에 곱하면 "멀리 그리고 빨리"만 보상된다 |
| 페이스 보너스 하한 2km | — | 400m 전력질주로 30% 보너스를 챙기는 경로 차단 |
| 고도 10m당 1pt, 상한 100 | — | 트레일 러너를 보상하되 기압계 노이즈가 누적되는 기기에서 점수가 폭주하지 않도록 상한을 둔다 |
| 세션 상한 1000pt | — | `validate_run`을 통과하는 범위 안에서도(예: 199km 울트라) 단일 세션이 레벨 곡선을 붕괴시키지 못하게 하는 최종 안전판 |

**스트릭 보너스는 넣지 않았다.** 스트릭을 포인트에 반영하려면 `compute_awarded_points`가 `profiles.current_streak_days`를 읽어야 하는데, 그 값은 같은 트랜잭션에서 `runs_recompute_stats`가 갱신하는 대상이라 읽는 시점에 따라 값이 달라진다(BEFORE 트리거에서는 아직 갱신 전). 순수 함수성이 깨지고 재현이 어려워진다. 스트릭 보상은 `streak_*` 뱃지 4종(총 3,410pt)이 충분히 담당한다.

`walk`/`indoor_run`도 동일 공식을 적용한다. 걷기는 페이스 보너스를 자연히 받지 못하고, 실내 러닝은 고도 보너스를 받지 못한다 — 별도 분기가 필요 없다.

## 4. 레벨 산식 확정

### 4.1 확정 공식 — 체증형

```
compute_level(p_total_points integer) RETURNS integer

RETURN least(
         1 + floor( power( greatest(p_total_points, 0)::numeric / 500.0, 1.0/1.6 ) ),
         100
       )::integer;
```

역함수(레벨 L 도달에 필요한 누적 포인트) — **UI 표시용으로 클라이언트도 동일 식을 쓴다:**

```
points_required(L) = ceil( 500 * (L - 1) ^ 1.6 )        -- L >= 1, points_required(1) = 0
```

**반영 대상:** `supabase/migrations/20260819140400_04_validation_and_stats.sql` — `compute_level()` 본문.
클라이언트 대응 구현: `lib/features/gamification/domain/level_curve.dart` (§8).

### 4.2 왜 선형을 버렸나

PLACEHOLDER(1000점당 1레벨)는 영구 선형이라 두 방향 모두에서 실패한다. 초반엔 첫 레벨업까지 러닝 7~8회가 걸려 신규 사용자가 아무 보상 없이 2~3주를 보내고, 후반엔 헤비 유저가 매달 2레벨씩 올라 레벨 숫자가 의미를 잃는다.

지수 `1.6`은 스킬 문서의 권장(`base * n^1.5`)에 가까우면서, 계수 `500`과 조합했을 때 아래 실측치가 나오도록 맞춘 값이다.

| 레벨 | 누적 필요 pt | 직전 레벨 대비 | 10km 러닝 환산(≈140pt) |
|---:|---:|---:|---:|
| 2 | 500 | 500 | 4회 |
| 3 | 1,516 | 1,016 | 11회 |
| 4 | 2,900 | 1,384 | 21회 |
| 5 | 4,595 | 1,695 | 33회 |
| 10 | 16,818 | 2,889 | 120회 |
| 20 | 55,588 | 4,607 | 397회 |
| 30 | 109,347 | 5,970 | 781회 |
| 50 | 253,096 | 8,214 | 1,808회 |
| 100 | 779,806 | 12,565 | 5,570회 |

레벨 2는 **첫 주 안에** 도달한다(러닝 4회 또는 러닝 2회 + 초반 뱃지 몇 개). 레벨 10은 반년~1년, 레벨 50 이상은 수년짜리 목표다.

경계값은 검산했다 — 모든 L에 대해 `compute_level(points_required(L)) = L`이고 `compute_level(points_required(L) - 1) = L - 1`이다. 두 식이 정확히 맞물린다.

**상한 100:** 상한이 없으면 UI가 3자리 레벨 배지를 감당해야 하고 만렙 개념이 사라진다. 100에 도달한 사용자의 `total_points`는 계속 누적된다.

> **[2026-08-20 업데이트]** `points` 랭킹 지표는 리더 결정으로 제거되었다(별도 요청 없이 처음부터
> 있던 지표였으나 불필요 판단). `total_points`는 레벨 산정 용도로만 남고, 포인트로 순위를 매기는
> 리더보드는 만들지 않는다. 아래 §5(동점 처리)의 `points` 지표 관련 서술은 역사적 기록으로 남긴다.

### 4.3 backend 구현 시 주의

- **`numeric`으로 계산할 것.** `power(1516/500.0, 0.625)`를 `double precision`으로 계산하면 경계값에서 2.9999999가 나와 레벨이 하나 낮게 나올 수 있다. `numeric` 캐스팅으로 경계를 안정화한다.
- `p_total_points = 0` → `power(0, 0.625) = 0` → 레벨 1. 정상.
- **임계값 테이블을 따로 만들지 말 것.** `compute_level`이 유일한 정본이다. 테이블이나 역함수를 별도로 두면 아래 함정에 빠진다.

  > ⚠️ **실제로 발견된 버그 — 역함수 `ceil(500 * (L-1)^1.6)`를 독립적으로 쓰면 안 된다.**
  > 클라이언트 구현 중 발견해 테스트로 잠갔다(`test/gamification/level_curve_test.dart`).
  > 지수 `1.6`이 이진 부동소수로 정확히 표현되지 않아 **L=33에서 `pow(32, 1.6)`이 정답 256보다
  > 약 3e-16 크게** 나오고, `ceil()`이 그 오차를 정수 1로 증폭해 `128001`을 반환한다.
  > 그런데 `compute_level(128000)`은 이미 33이다. 결과적으로 "레벨업까지 1pt 남음"이 표시된 뒤
  > 포인트가 늘어도 숫자가 그대로인 상태가 생긴다.
  >
  > 클라이언트는 `compute_level`을 기준으로 ±1 보정 루프를 돌려 정확한 역함수를 만들었다.
  > **backend가 "다음 레벨까지 필요한 포인트"를 서버에서 계산해 내려줄 일이 생기면 동일한 보정이
  > 필요하다.** `numeric` 연산이 `double precision`보다 안정적이지만 `ceil`의 증폭은 여전하다.
  > 현재 설계에서는 서버가 `level`만 내려주고 역함수는 클라이언트 전용이므로 문제가 되지 않는다.
- `compute_level` 호출 시점: `profiles.total_points`가 변하는 모든 경로(러닝 포인트 가산, 뱃지 포인트 가산, 챌린지 보상 포인트 가산) 이후 1회.

## 5. 랭킹 동점 처리 — `tie_break_value` 지표별 확정

### 5.1 backend §5.5 질의에 대한 회신

정렬 규약 자체는 **backend 제안대로 확정한다**: `score DESC → tie_break_value ASC → user_id ASC`, 표시는 `RANK()`(1,2,2,4). `user_id` 3차 정렬로 결정론적 순서를 만들어 `rank_delta`에 가짜 변동이 생기지 않게 한 판단에 동의한다.

문제는 지적하신 대로 `tie_break_value`가 전 지표에서 `sum(moving_seconds)`라는 점이다. **지표별로 다르게 정의한다:**

| `metric` | `score` | `tie_break_value` (작을수록 상위) | 사용자에게 설명하면 |
|---|---|---|---|
| `distance` | `sum(distance_meters)` | `sum(moving_seconds)` **(현행 유지)** | 같은 거리면 **빨리** 뛴 사람이 위 |
| `duration` | `sum(moving_seconds)` | **`-1 * sum(distance_meters)`** | 같은 시간이면 **멀리** 간 사람이 위 |
| `run_count` | `count(*)` | **`-1 * sum(distance_meters)`** | 같은 횟수면 **멀리** 간 사람이 위 |
| `points` | `sum(awarded_points)` | `sum(moving_seconds)` **(현행 유지)** | 같은 점수면 **짧은 시간**에 달성한 사람이 위 |

### 5.2 근거

**`duration`:** `score`가 이미 `sum(moving_seconds)`이므로 동점자는 총 이동 시간이 정확히 같다. 이때 자연스러운 서열은 "같은 시간에 더 멀리 간 사람" = 평균 페이스가 빠른 사람이다. 총 시간이 동일하므로 **평균 페이스 오름차순 정렬과 총 거리 내림차순 정렬은 순서가 완전히 동치**다. 거리 합이 더 싸고(추가 나눗셈 없음) 거리 0 예외 처리도 필요 없어 거리 합을 택했다.

**`run_count`:** 동점이 압도적으로 흔한 지표다(주간 3회 등). 여기서 `sum(moving_seconds)` 오름차순을 쓰면 **짧게 뛴 사람이 상위**가 되어 지표의 취지("많이 뛴 사람")와 정면으로 충돌한다. 총 거리 내림차순이 맞다.

**`distance` / `points`는 왜 그대로인가:** 두 지표 모두 "같은 성과를 더 적은 시간에" 낸 쪽을 우대하는 것이 자연스럽고, `sum(moving_seconds)`가 그 의미를 그대로 담는다.

### 5.3 부호 반전에 대한 주의사항

`duration`/`run_count`에서 `tie_break_value`가 **음수**로 저장된다(예: 총 12,345m → `-12345`). 컬럼 타입이 `double precision` nullable이고 제약이 없으므로 스키마 변경은 불필요하다.

> ⚠️ **flutter-ui-designer 필독:** `RankingEntry.tieBreakValue`는 **정렬 전용 내부 값이며 화면에 절대 표시하지 않는다.** 부가 정보가 필요하면 이미 존재하는 `runCount` / `totalMovingSeconds` 필드를 쓸 것. 모델 주석의 "작을수록 상위"는 여전히 정확하다 — 의미가 지표별로 다를 뿐이다.

`refresh_leaderboard()`의 SELECT 절에 지표별 `CASE`를 넣으면 된다:

```sql
CASE p_metric
  WHEN 'duration'  THEN -1 * sum(r.distance_meters)
  WHEN 'run_count' THEN -1 * sum(r.distance_meters)
  ELSE                   sum(r.moving_seconds)::double precision
END AS tie_break_value
```

## 6. 챌린지 완료 판정

### 6.1 진척 집계식 — `ChallengeType` 5종

**공통 집계 대상 러닝:**
```sql
WHERE r.user_id = p_user_id
  AND r.status = 'completed'
  AND r.is_flagged = false
  AND r.started_at >= c.start_at
  AND r.started_at <  c.end_at      -- 반열림 구간 [start_at, end_at)
```

귀속 기준이 `started_at`인 것은 §2.3 스트릭 규약과 동일하다. 챌린지 종료 직전에 출발해 종료 후에 끝난 러닝은 포함된다 — 사용자가 "마감 전에 출발했다"고 인식하는 쪽에 맞춘다.

| `ChallengeType` | `progress_value` 산식 | 단위 | 단조성 |
|---|---|---|---|
| `distance_total` | `sum(r.distance_meters)` | m | 증가만 |
| `run_count` | `count(*)` | 회 | 증가만 |
| `single_run_distance` | `max(r.distance_meters)` | m | 감소 가능(기록 삭제 시) |
| `streak_days` | 챌린지 기간 내 KST 러닝 일자의 **최장 연속 구간 길이** | 일 | 감소 가능 |
| `elevation_total` | `sum(coalesce(r.elevation_gain_meters, 0))` | m | 증가만 |

`streak_days`는 `profiles.current_streak_days`를 **쓰면 안 된다** — 그 값은 챌린지 기간 밖의 러닝까지 포함한다. §2.3의 gaps-and-islands 쿼리에 `started_at ∈ [start_at, end_at)` 조건만 추가해 기간 내에서 독립 계산한다.

### 6.2 `joined_at` 이전 기록도 포함한다

**확정: 참가 시점과 무관하게 챌린지 기간 전체의 러닝을 집계한다.** `challenge_participations.joined_at`은 집계 필터에 넣지 않는다.

근거: 챌린지 중반에 알게 된 사용자가 참가 즉시 진행률 0에서 시작하면, 이미 절반이 지난 챌린지에는 아무도 참가하지 않는다. 기간 전체를 집계하면 "참가만 하면 그동안 뛴 게 바로 반영된다"가 되어 참가 장벽이 사라진다. `joined_at`은 참가 이력 기록 용도로만 남는다.

### 6.3 갱신 시점

```
runs INSERT / UPDATE / DELETE (AFTER)
  → recompute_challenge_progress(p_user_id, p_run_id)
```

대상 챌린지를 좁혀야 한다 — 전체 챌린지를 매번 훑으면 챌린지 수에 비례해 업로드가 느려진다:

```sql
SELECT cp.*, c.*
FROM challenge_participations cp
JOIN challenges c ON c.id = cp.challenge_id
WHERE cp.user_id = p_user_id
  AND c.status IN ('upcoming', 'active')          -- ended/archived는 재계산하지 않음
  AND NEW.started_at >= c.start_at
  AND NEW.started_at <  c.end_at                  -- 이 러닝이 속한 챌린지만
```

**`ended`/`archived` 챌린지를 재계산하지 않는 이유:** 종료 후에 과거 날짜 러닝을 사후 업로드해 순위를 뒤집는 경로를 막는다. 오프라인 러닝의 지연 업로드는 정당한 사용 사례지만, 종료된 챌린지의 결과가 며칠 뒤에 바뀌면 이미 발표된 순위가 무의미해진다. **트레이드오프를 인지한 결정이다** — 종료 직전 러닝을 오프라인으로 기록하고 종료 후에 업로드한 사용자는 반영받지 못한다. 완화책으로 backend가 `end_at + 24h`까지 유예(`status`를 `ended`로 넘기는 배치를 24시간 지연)하는 것을 권장한다.

`participations` 자체 INSERT(신규 참가) 시에도 1회 호출해야 §6.2의 "과거 기록 즉시 반영"이 성립한다.

### 6.4 완료 확정과 보상

```sql
-- recompute_challenge_progress 내부, progress 갱신 직후
UPDATE challenge_participations
   SET progress_value = v_progress
 WHERE id = cp.id;

IF cp.completed_at IS NULL AND v_progress >= c.target_value THEN
    UPDATE challenge_participations SET completed_at = now() WHERE id = cp.id;

    -- 보상 포인트
    IF c.reward_points > 0 THEN
        UPDATE profiles SET total_points = total_points + c.reward_points WHERE id = p_user_id;
    END IF;

    -- 보상 뱃지 (카탈로그 조건 판정을 우회하는 직접 지급)
    IF c.reward_badge_id IS NOT NULL THEN
        INSERT INTO user_badges (user_id, badge_id, earned_at, source_run_id, is_seen)
        VALUES (p_user_id, c.reward_badge_id, now(), p_run_id, false)
        ON CONFLICT (user_id, badge_id) DO NOTHING;
    END IF;

    UPDATE profiles SET level = compute_level(total_points) WHERE id = p_user_id;
END IF;
```

**완료는 되돌리지 않는다.** `completed_at`이 한 번 세워지면 이후 `progress_value`가 목표 아래로 내려가도(기록 삭제, 사후 `is_flagged` 판정) NULL로 되돌리지 않는다. 근거는 §2.5와 동일 — 이미 축하받은 성취를 설명 없이 회수하는 것이 오탐 리스크보다 나쁘다. 명백한 어뷰징은 운영자가 수동 처리한다.

**`reward_badge_id`로 지급되는 뱃지는 카탈로그 조건과 무관하게 직접 INSERT된다.** 이런 챌린지 전용 뱃지는 `badges`에 `category = 'challenge'`, `criteria_type = 'challenge_completed_count'`, `threshold`를 도달 불가능한 큰 값(예: `999999`)으로 시드해서 `evaluate_badges`가 절대 자동 지급하지 않도록 해야 한다. 현재 카탈로그 29종에는 그런 항목이 없으므로, 챌린지 전용 뱃지를 만들 때 이 규칙을 적용할 것.

### 6.5 크루 대항전

`Challenge.crewId`가 있으나 `crews` 테이블이 없어 이번 범위 밖이다(§1.3과 동일 사유). 크루 합산 진척은 `challenge_participations`를 크루로 GROUP BY하면 되므로 스키마 변경 없이 확장 가능하다. `ChallengeParticipation.rank`(랭킹형 챌린지 순위) 채우기도 크루 기능과 함께 설계한다.

`lib/features/gamification/domain/*`의 계산식은 §3·§4·§1.1의 SQL 의사코드와 **1:1 대응**한다. backend가 SQL을 수정하면 이 파일들도 함께 수정해야 한다 — 두 곳이 갈라지면 사용자가 보는 진행률과 실제 획득 시점이 어긋난다.
