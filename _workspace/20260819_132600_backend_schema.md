## 3. RLS 정책표

모든 테이블 RLS 활성화. 정책이 없는 동작 = **거부**. `service_role`은 RLS를 우회하므로 별도 정책 없음.
익명(`anon`) 롤은 모든 테이블에서 GRANT를 회수했다 — Runnit은 로그인 사용자 전용.

| 테이블 | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| `profiles` | 전체 (`true`) | 본인 (`id = auth.uid()`) | 본인 | ❌ (auth.users 삭제 cascade만) |
| `runs` | **본인만** | 본인 | 본인 | 본인 |
| `badges` | 전체 | ❌ | ❌ | ❌ |
| `user_badges` | 본인만 | ❌ (서버 재검증 전용) | 본인 — 실질적으로 `is_seen`만 (가드 트리거) | ❌ |
| `challenges` | 공개(`crew_id is null`) + 본인 크루 | ❌ | ❌ | ❌ |
| `challenge_participations` | 본인만 | 본인 (참가) | ❌ (진척도는 서버) | 본인 (탈퇴) |
| `leaderboard_entries` | 전체 | ❌ | ❌ | ❌ |

정책 술어는 전부 `(select auth.uid())` 형태로 감쌌다. `auth.uid()`를 그대로 쓰면 행마다 재평가되지만
감싸면 InitPlan으로 한 번만 평가된다 (Supabase `auth_rls_initplan` 권고).

**타인의 러닝 원본은 어떤 경로로도 조회할 수 없다.** 타인에게 노출되는 것은
`profiles`의 공개 필드와 `leaderboard_entries`의 비정규화 스냅샷뿐이다.

### 3.1 서버 전용 필드 보호 — 왜 RLS만으로 안 되는가

RLS는 **행** 단위 제어라 "이 행은 UPDATE해도 되지만 `total_points`만은 안 된다"를 표현할 수 없다.
컬럼 GRANT는 PostgREST에서 관리가 번거롭고 에러가 불친절하다. 그래서 **BEFORE 트리거**로 막는다.

**예외를 던지지 않고 "조용히 되돌린다"를 택한 이유:** 클라이언트는 freezed가 만든 `toJson()`을
통째로 upsert한다. `AppUser.toJson()`에는 `total_*`이, `RunRecord.toJson()`에는 `awarded_points`가
**항상 포함된다.** 예외를 던지면 정상적인 프로필 수정조차 실패한다.

| 트리거 | 대상 | 강제 내용 |
|---|---|---|
| `profiles_guard` | `profiles` | 통계 8종 + `level` + `crew_id` + `created_at`/`id` 되돌림, `updated_at = now()` |
| `runs_guard` | `runs` | `id`/`user_id`/`created_at` 되돌림, `avg_pace_sec_per_km` 재계산, `is_flagged`/`flag_reason` 재판정, `awarded_points` 재산정 |
| `user_badges_guard` | `user_badges` | INSERT 시 `earned_at = now()`, UPDATE 시 `is_seen` 외 전부 되돌림 |
| `challenge_participations_guard` | `challenge_participations` | `joined_at`/`progress_value`/`completed_at`/`rank` 되돌림 |
| `challenge_participant_count` | `challenges` | 참가/탈퇴 시 `participant_count` 증감 |
| `runs_recompute_stats` | `profiles` | runs 변경 시 소유자 통계 캐시 재계산 |
| `on_auth_user_created` | `profiles` | 가입 시 프로필 자동 생성 |

서버측 함수는 트랜잭션-로컬 GUC `runnit.server_write='on'`으로 가드를 통과한다
(`public.is_server_write()`). `SET LOCAL`이라 트랜잭션 종료 시 자동 해제되고,
클라이언트에는 이를 설정할 경로가 없다.

### 3.2 오프라인 upsert 멱등성

`RunRecord.id`는 클라이언트 생성 UUID다. 업로드는
`from('runs').upsert(record.toJson(), onConflict: 'id')` 형태를 쓴다.

- 같은 기록을 몇 번 올려도 결과가 동일 → 멱등.
- 남의 `id`를 추측해 upsert하면 UPDATE 경로를 타는데, `runs_update_own`의 `USING`이
  `user_id = auth.uid()`를 요구하므로 타인 행은 매칭되지 않고 실패한다 → 덮어쓰기 불가.
- `user_id`는 `runs_guard`가 UPDATE 시 `OLD` 값으로 되돌리므로 소유권 이전도 불가.

## 4. `runs.samples` jsonb — 행 크기와 TOAST

**채택:** 리더 확정대로 `runs.samples` jsonb 단일 컬럼.

### 4.1 크기 추정

1Hz 샘플링 기준 1시간 러닝 ≈ 3,600 샘플. 샘플 1개의 JSON 표현은 키 이름 포함 약 180~260 바이트
(11개 필드, 대부분 실수). 따라서 **세션 1건의 `samples` 원문은 약 650KB~900KB**다.

### 4.2 TOAST 동작과 그 결과

Postgres는 행 크기가 약 2KB(`TOAST_TUPLE_THRESHOLD`)를 넘으면 큰 컬럼을 TOAST 테이블로
분리 저장하고 본체에는 포인터만 남긴다. `jsonb`의 기본 storage는 `EXTENDED`(압축+분리)다.
즉 `samples`는 **사실상 항상** out-of-line 저장되며 LZ 압축으로 실제 사용량은 원문의 20~35%
(세션당 약 150~300KB)로 줄어든다.

여기서 나오는 **가장 중요한 실무 결과**:

> TOAST된 컬럼은 SELECT 목록에 없으면 **아예 읽지 않는다.**
> 따라서 목록 조회 성능은 `samples` 크기와 무관하다 — **`select('*')`를 쓰지 않는 한.**

`select('*')`로 히스토리 1페이지(20건)를 받으면 응답이 **10~20MB**가 된다. 모바일에서 치명적이다.

### 4.3 조회 패턴 규약

| 용도 | 쿼리 | samples |
|---|---|---|
| 히스토리 목록 | `from('run_summaries').select().eq('user_id', uid).order('started_at', ascending: false)` | 제외 |
| 러닝 상세 | `from('runs').select().eq('id', runId).single()` | 포함 |
| 지도 썸네일 | `route_polyline` 사용 | 제외 |

`run_summaries` 뷰는 `samples`만 뺀 `runs`의 투영이며 `security_invoker = true`라 RLS가 그대로 적용된다.
`samples` 키가 없으면 `RunRecord.fromJson`은 `@Default(<RunSample>[])`로 빈 배열을 채우므로 모델과 호환된다.

### 4.4 별도 테이블로 전환해야 할 때와 그 경로

다음 중 하나가 발생하면 jsonb 전략의 한계에 도달한 것이다: (a) 샘플 단위 쿼리 요구가 생김
(예: "심박 160 이상 구간만 조회", 구간별 랩 분석 서버 계산), (b) 부분 업데이트 요구
(러닝 중 샘플을 실시간 append — jsonb는 매번 전체 값을 다시 써야 하므로 write 증폭이 크다),
(c) PostGIS 공간 인덱스로 경로 검색.

전환 경로는 무중단으로 설계 가능하다. ① `run_samples (run_id, seq, ...)` 테이블을 새 마이그레이션으로
추가하고 `(run_id, seq)` PK를 건다. ② `jsonb_array_elements(samples)`를 소스로 하는 백필 배치를
`run_id` 범위로 나눠 돌린다. ③ 읽기 경로를 "테이블에 행이 있으면 테이블, 없으면 jsonb"로
분기하는 뷰/함수로 감싸 클라이언트 코드를 건드리지 않는다. ④ 백필 완료 후 쓰기 경로를 테이블로 전환하고,
검증 기간이 지나면 `samples` 컬럼을 드롭한다. 컬럼 드롭은 파괴적 변경이므로 반드시 사용자 승인 후.

## 5. 리더보드 성능 전략

### 5.1 캐시 테이블을 택한 이유 (MV·실시간 집계 대비)

| 방식 | 기각/채택 사유 |
|---|---|
| 매 조회 시 집계 | 사용자·기록 수에 선형. `myRank` 조회는 전체 정렬이 필요해 특히 나쁘다. **기각** |
| Materialized View | `REFRESH`가 전체 재계산이고 스코프/기간별 부분 갱신이 불가. 무엇보다 **`rank_delta`(직전 집계 대비 변동)를 계산할 수 없다** — MV는 이전 상태를 보존하지 않는다. **기각** |
| **일반 테이블 + UPSERT** | 스코프/기간별 부분 갱신 가능, UPSERT의 `DO UPDATE`에서 기존 행의 `rank`를 읽어 `rank_delta` 산출 가능, Realtime 구독 가능. **채택** |

### 5.2 갱신 함수

```
refresh_leaderboard(p_period, p_metric, p_scope, p_crew_id, p_anchor) -> integer
refresh_all_leaderboards(p_anchor) -> void      -- cron 진입점
```

두 함수 모두 `anon`/`authenticated`에서 EXECUTE를 회수했다 — 클라이언트가 RPC로 호출할 수 없다.

집계 대상: `status = 'completed' AND is_flagged = false AND started_at ∈ [period_start, period_end)`.
`runs_completed_period_idx`(부분 인덱스)가 이 술어를 그대로 커버한다.

`score` 산식: distance→`sum(distance_meters)`, duration→`sum(moving_seconds)`,
run_count→`count(*)`.

> **[2026-08-20]** `points`(→`sum(awarded_points)`) 지표는 리더 결정으로 제거했다. 참고로 애초에
> 이 산식은 `runs.awarded_points` 합산만 하고 뱃지/챌린지 보너스를 빠뜨리고 있어
> `profiles.total_points`(레벨 산정 기준)와 어긋나는 결함이 있었다 — 종단 테스트로 발견했으나
> 지표 자체가 없어지면서 별도 수정은 하지 않았다. 향후 포인트 기반 랭킹을 다시 추가한다면
> 이 불일치부터 해결해야 한다(뱃지/챌린지 포인트도 기간 필터링해 합산하거나, `total_points`
> 스냅샷을 별도 경로로 반영하거나).

갱신 후 `computed_at < v_now`인 잔여 행을 삭제해 탈락자를 정리한다.

### 5.3 스케줄

`pg_cron` 5분 주기를 기본값으로 제안한다(03 파일에 주석으로 준비, 원격 반영 시 활성화).
초기 규모에서 단순함이 최우선이라는 판단이다. 갱신 소요가 주기의 30%를 넘기 시작하면
`daily`/`weekly`만 잦게, `monthly`/`all_time`은 시간 단위로 분리한다.

Realtime으로 `leaderboard_entries`를 구독하면 폴링이 없어지지만, **갱신이 5분 배치이므로
체감 실시간성은 배치 주기에 종속된다.** UI에 `computed_at` 기준 "N분 전" 표기를 반드시 함께
노출할 것 — flutter-ui-designer 협의 필요.

### 5.4 규모 한계

현재는 기간 내 기록이 있는 **모든** 사용자를 실체화한다. `myRank`가 상위 N 밖에서도
동작해야 하기 때문이다. 사용자 10만 명 × 4기간 × 4지표 규모에 도달하면 상위 N(예: 500)만
실체화하고, 순위권 밖 사용자는 `count(*) FILTER (WHERE score > 내 score) + 1` 단건 쿼리로
계산하는 하이브리드로 전환한다.

### 5.5 동점 처리 (gamification 확인 대기)

리더 확정: `score` DESC → `tie_break_value` ASC → `user_id` ASC, 표시는 `RANK()`(1,2,2,4).
`user_id` 3차 정렬은 동점자 순서를 결정론적으로 만들어 **갱신마다 순위가 흔들리는 것을 막는다**
(흔들리면 `rank_delta`에 가짜 변동이 생긴다).

⚠️ **gamification-designer 확인 대기 항목:**
현재 `tie_break_value`는 모든 지표에서 `sum(moving_seconds)`다. `metric = 'duration'`일 때는
`score`와 같은 값이라 사실상 tie-break가 작동하지 않는다(`user_id`로 넘어간다).
duration 지표의 보조 기준(예: 총 거리 내림차순)을 gamification-designer가 확정해야 한다.

### 5.6 기간 경계 — Asia/Seoul 고정

`leaderboard_period_bounds(period, anchor)`가 반열림 구간 `[start, end)`를 반환한다.

| period | 경계 |
|---|---|
| daily | KST 00:00 ~ 익일 00:00 |
| weekly | `date_trunc('week')` = **ISO 8601 월요일** 00:00 KST ~ 익주 월요일 |
| monthly | KST 1일 00:00 ~ 익월 1일 |
| all_time | `1970-01-01T00:00:00Z` ~ `9999-12-31T23:59:59Z` |

> **`'infinity'::timestamptz`를 쓰지 않았다.** PostgREST가 `"infinity"` 문자열로 직렬화하면
> Dart의 `DateTime.parse`가 `FormatException`을 던진다. `RankingEntry.periodEnd`는 non-null
> `DateTime`이므로 파싱 가능한 센티넬 값이 필요하다.

## 6. 서버 재검증 (부정행위 방지)

`public.validate_run(...)`이 사유 문자열 또는 NULL을 반환하고, `runs_guard`가 매 INSERT/UPDATE마다
호출해 `is_flagged`/`flag_reason`을 세운다. **기록은 삭제하지 않는다** — 오탐 시 사용자 문의에
대응할 근거가 남아야 한다. 플래그된 기록은 랭킹·프로필 통계·포인트 집계에서만 빠진다.

| 사유 | 조건 | 근거 |
|---|---|---|
| `moving_exceeds_elapsed` | `moving > elapsed` | 물리적으로 불가능 |
| `zero_moving_time` | `distance > 0 AND moving <= 0` | 페이스 분모가 0 |
| `implausible_avg_speed` | `distance >= 400 AND distance/moving > 7.0 m/s` | 7.0 m/s = 2'23"/km. 마라톤 세계기록 평균이 약 5.7 m/s |
| `implausible_max_speed` | `max_speed_mps > 15.0` | 54 km/h. 인간 최고 순간속도(약 12 m/s) 초과 |
| `implausible_distance` | `distance > 200,000 m` | 단일 세션 200km 초과 = 기록 병합 오류 |
| `implausible_duration` | `elapsed > 86,400 s` | 24시간 초과 |
| `implausible_elevation_gain` | `gain > 9,000 m` | 에베레스트 고도 초과 |

400m 미만은 평균속도 검사에서 제외했다 — 짧은 구간은 GPS 오차의 상대적 영향이 커서 오탐이 많다.

**`avg_pace_sec_per_km`는 플래그 대상이 아니라 정규화 대상이다.** 서버가
`moving_seconds / (distance_meters/1000)`으로 무조건 재계산해 덮어쓴다. 불일치를 플래그로 처리하면
단순 반올림 차이로 정상 기록이 랭킹에서 빠진다.

**포인트/레벨은 PLACEHOLDER다.** `compute_awarded_points()`(정상 완료 기록 100m당 1점),
`compute_level()`(1000점당 1레벨). gamification-designer가 확정 규칙을 회신하면 이 두 함수
본문만 교체하면 되고 호출부는 건드릴 필요 없다.

## 7. 인덱스 근거

| 인덱스 | 대상 쿼리 |
|---|---|
| `runs_user_started_idx (user_id, started_at desc)` | 히스토리 목록. `user_id` 등치 + `started_at` 정렬을 한 인덱스로 커버해 정렬 노드를 제거 |

| `runs_user_completed_idx (user_id, ended_at) WHERE completed AND NOT flagged` | `recompute_profile_stats`의 사용자별 전체 집계 + 스트릭 날짜 추출 |
| `profiles_username_lower_idx` | 대소문자만 다른 핸들 중복 방지 |

| `user_badges_user_earned_idx (user_id, earned_at desc)` | 뱃지 갤러리 |
| `user_badges_unseen_idx WHERE NOT is_seen` | 미확인 뱃지 큐. 부분 인덱스라 매우 작다 |
| `user_badges_badge_id_idx`, `user_badges_source_run_idx`, `challenges_reward_badge_idx`, `challenge_participations_*` | **FK 커버 인덱스.** 인덱스 없는 FK는 부모 행 DELETE 시 자식 전체 스캔을 유발한다 (Supabase `unindexed_foreign_keys` 권고) |
| `leaderboard_entries_read_idx (scope, crew_key, period, metric, period_start, rank)` | 리더보드 페이지 조회 — 필터 전부 + rank 정렬 커버 |
| `leaderboard_entries_user_idx (user_id, period, metric)` | `myRank` 단건 조회 |

## 8. 클라이언트 쿼리 레시피 (qa-integration-tester 참고)

```dart
// 히스토리 목록 — samples 제외 필수
supabase.from('run_summaries').select()
  .eq('user_id', uid).order('started_at', ascending: false).range(0, 19);

// 러닝 상세 — samples 포함
supabase.from('runs').select().eq('id', runId).single();

// 러닝 업로드 (오프라인 멱등)
supabase.from('runs').upsert(record.toJson(), onConflict: 'id').select().single();
//   -> 응답에 서버가 확정한 awarded_points / avg_pace_sec_per_km / updated_at 이 담겨온다.

// 리더보드
supabase.from('leaderboard_entries').select()
  .eq('scope', 'global').eq('period', 'weekly').eq('metric', 'distance')
  .order('rank').range(0, 49);

// 내 순위
supabase.from('leaderboard_entries').select()
  .eq('user_id', uid).eq('scope', 'global').eq('period', 'weekly')
  .eq('metric', 'distance').maybeSingle();

// 뱃지 (카탈로그 임베드)
supabase.from('user_badges').select('*, badge:badges(*)')
  .eq('user_id', uid).order('earned_at', ascending: false);

// 챌린지 참가 현황
supabase.from('challenge_participations').select('*, challenge:challenges(*)')
  .eq('user_id', uid);
```

**주의:** `period_start`를 필터에 넣지 않으면 과거 기간 행까지 섞인다. 현재 기간만 원하면
클라이언트가 KST 경계를 계산하기보다 `.eq('period_start', ...)`를 생략하고
`.order('period_start', ascending: false)` + `.limit()`으로 최신 기간을 잡는 편이 안전하다.

## 9. architect 계약과의 불일치 / 조율 필요 항목

| # | 항목 | 상태 |
|---|---|---|
| 1 | `runs.is_flagged` / `flag_reason` | 모델에 없는 서버 전용 컬럼 추가. `fromJson`은 미인식 키를 무시하므로 무해하나, **architect가 모델에 읽기 전용 필드로 추가할지 결정 필요.** 현재는 클라이언트가 "왜 내 기록이 랭킹에 없는지" 알 수 없다 |
| 2 | `leaderboard_entries.crew_key` | 모델에 없는 내부 생성 컬럼. NULL `crew_id`의 UPSERT 충돌 추론을 위해 필요. `fromJson` 무해 |
| 3 | `AppUser.crewId` 쓰기 권한 | `crews` 테이블 미정의라 클라이언트 변경을 차단했다. 크루 기능 착수 시 가입/탈퇴 RPC를 별도 설계해야 한다 |
| 4 | `RunRecord.avgPaceSecPerKm` | 계약서에는 클라이언트 필드로 되어 있으나 **서버가 재계산해 덮어쓰도록 했다.** 파생값이므로 정합성 우선. architect 확인 요청 |
| 5 | `RankingScope.friends` | 친구 관계 테이블이 없어 `refresh_leaderboard`가 예외를 던진다. 모델에는 값이 존재하므로 UI가 friends 탭을 노출하면 빈 결과가 된다 |
| 6 | `Badge.criteriaType` | gamification-designer 확정 전이라 enum이 아닌 자유 `text`. 확정 후 CHECK 제약 추가 권장 |
| 7 | `tie_break_value` (duration 지표) | §5.5 참조. **gamification 확인 대기** |
| 8 | 포인트/레벨 산식 | PLACEHOLDER. **gamification 확인 대기** |
| 9 | `createdAt`/`updatedAt` 명시적 NULL | 모델이 nullable이라 `toJson()`이 명시적 `null`을 보낸다. Postgres는 **명시적 NULL 입력 시 DEFAULT를 적용하지 않으므로** NOT NULL 위반이 났을 것이다. 가드 트리거의 `coalesce`로 해결했다. **모델 변경 불필요하나 architect가 알아야 할 함정** |

## 10. 사용자 승인이 필요한 후속 작업

1. **원격 Supabase 프로젝트 생성 및 마이그레이션 적용** — 이번 단계는 로컬 SQL까지다.
