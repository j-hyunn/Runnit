## 1. 문제 — v1.6이 실제로는 반만 막혀 있었다

PRD v1.6은 "사용자는 러닝을 삭제할 수 없고, 저장된 러닝은 제목·메모만 수정 가능"을 확정했다. 그런데 라이브 스키마에서 실제로 막혀 있던 것은 **삭제 의도**뿐이었고(그것조차 `runs_delete_own` 정책이 남아 있었다), **수정 경로는 사실상 무제한**이었다.

원인은 업로드 아키텍처 그 자체다. 업로드는 Edge Function이 아니라 **클라이언트 UUID를 PK로 쓰는 멱등 upsert**다(ARCHITECTURE §5.2). 멱등이라는 말은 곧 **UPDATE 경로가 항상 열려 있다**는 뜻이다. 그런데 `trg_runs_guard`(마이그레이션 05 → 39-6)의 UPDATE 분기가 고정하는 것은 세 개뿐이었다.

```sql
new.id         := old.id;
new.user_id    := old.user_id;
new.created_at := old.created_at;
```

`distance_meters` · `moving_seconds` · `elapsed_seconds` · `samples` · `started_at` · `status` · `activity_type` · `device_vendors`는 전부 클라이언트 UPDATE로 바뀔 수 있었다.

**"파생값은 어차피 재계산되니 괜찮지 않나"가 함정이다.** 가드는 페이스·`validate_run`·`compute_run_xp`를 다시 돌린다. 그래서 결과는 언제나 정합적이다 — 다만 그것은 **조작된 원본에 대한 정합성**이다. 3km 러닝을 정상 업로드한 뒤 같은 `id`로 `distance_meters = 42195`를 UPDATE하면, 가드가 성실하게 페이스와 XP를 다시 계산해 주고 `runs_01_recompute_stats` → `recompute_season_tier`가 티어를 올리고, `refresh_all_leaderboards`가 랭킹에 반영하고, `runs_03_evaluate_badges`가 뱃지를 지급한다. 게다가 v1.6이 확정한 **티어 단조 증가**(마이그레이션 43) 때문에 나중에 부정 판정이 나도 등급은 시즌 내내 내려가지 않는다 — 즉 이 구멍은 **되돌릴 수 없는 이득**을 만든다.

## 2. 설계 결정

### 2.1 강제 지점 = BEFORE 트리거 하나 (RLS·컬럼 GRANT 아님)

| 후보 | 기각 사유 |
|---|---|
| RLS 정책 강화 | RLS는 **행 단위** 술어다. "이 행은 UPDATE 가능하되 `title`/`note` 컬럼만"은 표현할 수 없다 (05 헤더가 이미 같은 결론) |
| 컬럼 단위 GRANT (`grant update (title, note)`) | 오프라인 재 upsert가 **행 전체**를 보낸다. 권한 없는 컬럼이 payload에 있으면 요청 전체가 42501로 거부 → **멱등 동기화 큐가 영구 실패**한다 |
| 전용 RPC (`update_run_meta`) | 별도 경로가 늘고, 기존 upsert UPDATE 경로는 **여전히 열린 채**다. 구멍을 막지 못하면서 표면만 늘린다 |
| **BEFORE UPDATE 트리거에서 되돌리기** | ✅ 채택. 경로가 몇 개든 최종 관문 하나를 통과하므로 구멍이 없다 |

### 2.2 예외(raise)가 아니라 "되돌리기(무시)"

`05_server_guards.sql` 헤더가 세운 방침의 직접적 연장이다. 클라이언트는 freezed `toJson()` 전체를 upsert하고, `syncPending()`은 그 멱등성을 재시도의 근거로 삼는다. 여기서 422/403을 던지면 **정상적인 재시도까지 영구 실패**한다.

- 값이 같은 재 upsert(= 오프라인 큐) → 되돌려도 결과 동일 → 무해
- 실제 편집 시도 → 조용히 무시
- 클라이언트가 `title`/`note`만 부분 UPDATE → 정상 반영

### 2.3 블랙리스트가 아니라 화이트리스트 (`new := old`)

```sql
v_title := new.title;
v_note  := new.note;
new       := old;      -- 전체 되돌리기
new.title := v_title;  -- 허용 컬럼만 재적용
new.note  := v_note;
```

`runs`는 계속 컬럼이 늘어 왔다(36 `device_vendors`, 39 `awarded_xp`). 블랙리스트로 열거하면 **컬럼을 추가한 사람이 이 파일을 고치는 것을 잊는 순간 구멍이 생긴다.** 행 통째 대입은 신설 컬럼을 자동으로 보호한다.

`jsonb_populate_record(old, …)` 대신 `new := old`를 쓴 이유: json 왕복을 아예 없애 enum 배열(`device_vendors`)·`jsonb`(`samples`)·`timestamptz`의 변환 손실 가능성을 제거했고, plpgsql 순수 행 대입이라 폴리모픽 타입 추론 이슈도 없다.

### 2.4 순서 — 되돌리기가 파생값 재계산보다 **먼저**

되돌린 뒤에 페이스·`validate_run`·`compute_run_xp`가 돌므로 전부 `old`의 원본값을 근거로 계산된다. 결과는 최초 업로드 때와 완전히 같은 값으로 수렴한다. 즉 **편집 UPDATE는 파생값을 흔들지 않는다.** AFTER 트리거(`runs_01`~`_04`)는 그대로 돌지만 전부 멱등 재집계라 같은 값으로 다시 쓰고 끝난다.

### 2.5 잠금 범위 = 터미널 상태 + 클라이언트 경로

```sql
if not public.is_server_write()
   and old.status in ('completed', 'discarded')
```

- `is_server_write()` 예외: 부정 판정·재집계·백필이 지나가야 한다.
- `recording`/`paused` 제외: 현재 클라이언트는 완료 기록만 업로드하므로(`LocalRunRepository.save`) 서버 행은 항상 이미 터미널이다. 다만 향후 체크포인트 업로드가 생기면 그 경로는 정상적으로 원본을 갱신해야 하므로 방어적으로 열어 둔다.

### 2.6 길이 상한 — CHECK는 백스톱, 강제는 가드가

TRD에 기존 근거값이 없어 이번에 확정했다.

| 컬럼 | 상한 | 근거 |
|---|---|---|
| `title` | 60자 | 한 줄 제목. 목록 카드/공유 카드에서 줄바꿈 없이 읽히는 상한 |
| `note` | 500자 | 짧은 회고 메모. TOAST 임계(≈2KB)에 한참 못 미쳐 저장 비용 무시 가능 |

가드가 `btrim` → `left(…, 상한)` → 빈 문자열은 `NULL`로 정규화한다. **절단 전에 trim**해야 "60자 + 공백"이 공백만 남기고 잘리는 일이 없다. CHECK 제약(`runs_title_len`/`runs_note_len`)은 서버 경로·수동 SQL을 위한 백스톱이며, 정상 클라이언트 경로에서는 절단이 먼저 일어나 400을 받지 않는다 — **거부 대신 절단**을 택한 것도 오프라인 큐 영구 실패를 막기 위함이다.

기존 데이터에 상한 초과분이 있을 수 있으므로 제약 추가 전에 `update … set title = left(title, 60)`으로 절단한다.

### 2.7 `runs_delete_own` 정책 삭제 — GRANT는 유지

`07_rls.sql`의 `runs_delete_own`은 v1.5 이전(HI-07 = "수정/삭제") 사양의 잔재다. 정책을 내린다.

⚠️ **테이블 GRANT는 일부러 회수하지 않았다.** `revoke delete on public.runs from authenticated`를 하면 PostgREST가 42501을 던지고 `guardSupabase`가 `Failure.unauthorized`로 올린다. `LocalRunRepository.delete()`는 두 곳에서 쓰이는데

- `TrackingController.discard()` (`tracking_providers.dart:167`)
- 미완결 세션 배너의 "버리기" (`tracking_page.dart:1223`)

둘 다 **아직 업로드된 적 없는 `recording`/`paused` 체크포인트**를 지운다(`save()`가 완료 기록만 서버로 보낸다). 즉 서버 DELETE는 원래도 0행이었다. 정책만 내리면 RLS 술어에 매칭되는 행이 없어 **에러 없이 0행**으로 끝나므로 보안 효과는 같고 기존 흐름은 그대로다.

## 3. 프런트엔드 계약

| 항목 | 계약 |
|---|---|
| 편집 API | 별도 RPC 없음. 기존 `runs` 테이블 경로 그대로 |
| 권장 호출 | `from('runs').update({'title': …, 'note': …}).eq('id', id).select('id,title,note,updated_at').single()` |
| 전체 행 upsert | 허용됨(오프라인 큐 그대로). `title`/`note` 외 필드는 **조용히 무시**된다 |
| 무시되는 필드 | 터미널 상태 행의 `title`·`note`를 뺀 **전부**. 대표적으로 `distance_meters` · `moving_seconds` · `elapsed_seconds` · `samples` · `route_polyline` · `started_at` · `ended_at` · `status` · `activity_type` · `sources` · `device_vendors` · 심박/케이던스/칼로리 |
| 에러 표면화 | **없음.** 무시는 4xx가 아니다. 사용자에게 "수정할 수 없습니다" 토스트를 띄우려면 클라이언트가 UI에서 애초에 편집을 제한해야 한다 |
| 재조회 필요 여부 | **불필요.** BEFORE 트리거가 같은 트랜잭션에서 정규화하므로 `.select().single()` 응답이 곧 서버 확정값이다 (`is_flagged` 되받는 기존 패턴과 동일) |
| 정규화 부작용 | 서버가 `btrim` + 절단 + 빈 문자열→`NULL`을 적용한다. 클라이언트가 보낸 문자열과 응답이 다를 수 있으므로 **응답값을 로컬에 반영**할 것 |
| 길이 제한 | `title` 60자 / `note` 500자. UI에서 `maxLength`로 먼저 막는 것을 권장(서버는 조용히 자른다) |
| 삭제 | 저장된(업로드된) 러닝의 서버 삭제는 **불가**. `RunRepository.delete()`는 미완결 세션 폐기 전용으로 의미를 좁혀야 한다 — 완료 기록에 호출하면 로컬 행만 사라지고 서버 행이 남아 다음 원격 조회에서 되살아난다 |
| `updated_at` | 편집 시 서버가 `now()`로 갱신. 목록 정렬 키는 여전히 `started_at`이므로 편집이 순서를 바꾸지 않는다 |

### 클라이언트 후속 작업 (이 작업 범위 밖)

1. `RunRepository`에 `updateMeta(String id, {String? title, String? note})` 추가 — 전체 행 upsert가 아니라 부분 UPDATE여야 3600 샘플 재전송을 피한다.
2. 로컬 drift 행의 `summaryJson`에도 같은 값을 반영(오프라인 편집 → `syncPending` 재시도 경로 포함).
3. `RunRepository.delete()`의 문서/시그니처를 "미완결 세션 폐기 전용"으로 좁히거나 `discardInterrupted()`로 개명.
4. 상세 화면(`run_detail_page.dart`)에 편집 진입점 + `maxLength` 60/500.

### 4.1 QA 지적 반영 (2026-08-31, `_workspace/20260831_183000_qa_hi07.md`)

**C-5 (CONFIRMED) — 51-1의 사전 절단 UPDATE가 AFTER 트리거 4종을 전량 깨운다.** `runs_01_recompute_stats`·`_02_challenge_progress`·`_03_evaluate_badges`·`_04_notifications`은 전부 `for each row`이고 **`WHEN` 절이 없다.** 정리 UPDATE가 `is_server_write()`를 켜지 않으면 매칭 행마다 티어 재계산 + 챌린지 진척 + 미획득 뱃지 전량 재평가 + 알림 인큐가 돈다. 중복 푸시는 `unique(user_id, dedupe_key)`가 막지만, 마이그레이션이 임의 사용자의 집계를 대량 재계산하는 것은 의도가 아니고 `source_run_id` 오귀속 위험도 있다.

→ 절단 UPDATE 두 건을 `do $$ … $$` 블록으로 묶고 `perform set_config('runnit.server_write','on', true)`로 감쌌다(트랜잭션 로컬이라 종료 시 자동 해제). 위 사전 조회를 마이그레이션 주석과 이 체크리스트에 명시했다.

**L-3 (PLAUSIBLE) — `recording`/`paused` 예외.** 현재는 `save()`가 완료 기록만 올려 도달 불가지만, 체크포인트 업로드가 생기면 "recording INSERT → 자유 UPDATE로 원본 조작 → completed 확정"이 열린다. 51-2에 경고 주석을 추가했다 — 도입 시 진행 중 행에도 단조 증가 잠금을 걸거나 확정 전환을 전용 RPC로 좁혀야 한다.

**L-1 / L-2 (미반영, 판단 근거)**: 편집 UPDATE마다 재집계 체인이 도는 비용은 실재하지만, 제안된 `WHEN` 절은 "집계에 영향을 주는 컬럼"의 **열거형 화이트리스트**라 §2.3에서 피하려던 함정과 같은 성질을 갖는다 — 컬럼이 늘 때 이 절을 갱신하는 것을 잊으면 이번엔 *집계가 조용히 누락*된다(구멍보다 진단이 어려운 실패 모드다). 결과는 멱등이라 값이 흔들리지 않고, 편집은 러닝 업로드보다 드문 동작이다. **비용이 실측으로 문제가 될 때** 트리거 4종을 한 번에 다루는 별도 마이그레이션으로 처리하는 편이 낫다고 판단해 이번 범위에서 제외했다(L-2는 L-1과 같은 원인이라 함께 해소된다).
