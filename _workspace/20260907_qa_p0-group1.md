## 1. 모델 ↔ 스키마 (`client_reported` jsonb ↔ `ClientReportedRun`) — PASS

실 서버(`xwtbwexcofcgmbvktwdo`)에서 `runs`의 실제 컬럼 타입과 트리거가 만드는 jsonb 모양을 직접 재현해 대조했다.

서버가 만드는 모양 (`supabase/migrations/20260903120000_64_server_distance_recalc.sql:369`, 실측 렌더링):

```json
{"max_speed_mps": null, "moving_seconds": 0, "distance_meters": 0,
 "recalculated_at": "2026-09-07T07:42:42.737771+00:00"}
```

| 서버 키 | 서버 타입 | Dart 필드 | 생성 파서(`run_record.g.dart:9`) | 판정 |
|---|---|---|---|---|
| `distance_meters` | `double precision` | `double? distanceMeters` | `(json[...] as num?)?.toDouble()` | ✅ |
| `moving_seconds` | `integer` | `int? movingSeconds` | `(json[...] as num?)?.toInt()` | ✅ |
| `max_speed_mps` | `double precision` (null 가능) | `double? maxSpeedMps` | `(json[...] as num?)?.toDouble()` | ✅ |
| `recalculated_at` | `timestamptz` → ISO8601 `+00:00` | `DateTime? recalculatedAt` | `DateTime.parse(...)` | ✅ |

- `@JsonSerializable(fieldRename: FieldRename.snake)`가 camelCase↔snake_case를 정확히 뒤집는다 (TRD §4.1 규약 준수).
- **정수 렌더링 안전**: Postgres가 `0.0`을 jsonb `0`으로 내려도 `num?.toDouble()`이라 캐스트 예외가 없다. 모델 테스트 `PostgREST가 정수로 내려준 거리도 double로 받는다`가 정확히 이 지점을 잡고 있다.
- **null 케이스**: 4필드 전부 nullable, 컬럼 자체가 null이면 `clientReported == null`. 테스트 `컬럼이 null이면 필드도 null이다` 확인.
- 서버가 값을 채우는 조건(`new.client_reported is null and abs(diff) >= 1.0`, 마이그레이션 64:367)이 모델 주석·TRD §3.2 서술("작고 차이가 1m 이상일 때 최초 한 번만")과 일치.

⚠️ **UNVERIFIED-1**: `select client_reported from runs where client_reported is not null limit 5` → **0건**. 마이그레이션 64 원격 적용 이후 실제로 거리가 깎인 기록이 아직 없다. 따라서 위 판정은 DDL·트리거 코드와 타입 재현으로 내린 것이고, **PostgREST가 이 컬럼을 실제로 `Map<String, dynamic>`으로 내려주는지는 실 왕복으로 확인하지 못했다.** (관련: PLAUSIBLE-2)

## 3. G-4 인플라이트 표식 수명 — PASS (누수 없음)

`_localEditDuringUpload`의 누수 가능성을 세 갈래로 따졌고 전부 안전하다.

- **early-return이 `try` 밖이다**: `_push`(:274) `if (!_inFlight.add(record.id)) return false;`가 `try` 진입 **전**이라, 중복 호출이 `finally`에 들어가 **남의 표식을 지우지 않는다.** 이 배치가 틀렸다면 인플라이트 중복 호출 한 번이 G-4 방어를 무력화했을 것이다.
- **`finally`의 두 `remove` 사이에 `await`가 없다**(:287-288) → `_applyMeta`(:567)의 `if (_inFlight.contains(id)) _localEditDuringUpload.add(id)`가 그 틈에 끼어들어 표식만 남기는 인터리빙이 불가능하다(Dart 단일 스레드).
- **다른 id 인터리빙**: 두 집합 모두 id 키이고 `_push`는 `record.id`만 다룬다. 실패 경로(`_markUploadFailed`)도 같은 `finally`를 지난다.
- **`editedDuringUpload=true`일 때 `syncAttempts: 0` 복원**(:380)이 함께 걸려 있어, 편집 재업로드가 남은 예산 안에서만 시도되는 문제도 없다.

회귀 2건(`업로드 중 제목을 고치면 synced로 올리지 않고 pending으로 남긴다` / `업로드 중 편집이 없으면 종전대로 synced로 올린다`)이 양방향을 잡는다.

## 5. 모델 getter ↔ 위젯 (ui 보고 #3) — PASS

`_SummaryGrid`(:194)의 `record.clientReportedDistanceMeters!` 강제 언랩은 **안전하다**:

```dart
double? get clientReportedDistanceMeters =>
    distanceWasAdjusted ? clientReported!.distanceMeters : null;
```

- `distanceWasAdjusted`는 `clientReported?.distanceMeters`가 null이면 즉시 false를 돌려주므로, true인 경로에서 `clientReported!`와 `.distanceMeters`가 모두 non-null임이 보장된다.
- 위젯이 `record.distanceWasAdjusted ? ... clientReportedDistanceMeters! ...`로 **같은 술어로 게이트**하므로 두 언랩 모두 도달 불가능한 null이 없다.
- 임계 `> 10.0`(초과)과 테스트 `정확히 임계값이면 병기하지 않는다`가 일치. 축소 방향만 보는 것도 서버 `least(recalc, claimed)`(마이그레이션 64:359)와 정합.

# 발견 사항

## CONFIRMED-1 — G-4가 `flagged + pending`을 실제 도달 가능하게 만들었는데, 배타 규칙의 근거 주석과 재시도 탈출구가 그대로다

**파일**: `lib/features/history/presentation/run_detail_page.dart:354-364`

```dart
// 플래그가 우선이다 — 두 배너를 함께 띄우지 않는다. 검토 대상 기록은
// 업로드가 끝났다는 뜻이므로 애초에 동시에 성립하기 어렵고, 겹칠 경우
// ...
if (record.isFlagged == true) ...[
  const _FlaggedBanner(),
] else if (isSyncPending(record, syncStatus: syncStatus)) ...[
  _SyncPendingBanner(failed: ..., onRetry: retryExhausted ? ... : null),
],
```

**재현 경로 (코드로 확인됨)**

1. 업로드 인플라이트 중 사용자가 제목/메모를 고친다 → `_applyMeta`(`local_run_repository.dart:567`)가 `_localEditDuringUpload`에 표식.
2. 서버 응답이 도착 → `applyServerConfirmation(editedDuringUpload: true)`가 **`is_flagged`는 `_adoptedKeys`로 채택**(:363)하면서 **`sync_status`는 `pending`으로 남긴다**(:371).
3. 결과 행: `isFlagged == true && syncStatus == pending`. `runRecordFromRow`가 그대로 모델로 올린다.
4. 상세 화면은 `_FlaggedBanner`만 띄우고 `_SyncPendingBanner`를 **`else` 가지에서 통째로 건너뛴다** → 사용자는 "이 기록이 아직 안 올라갔다"는 사실을 전혀 듣지 못한다.
5. 이후 편집 재업로드가 `maxSyncAttempts`(10)회 실패하면 `syncPending()` 질의에서 영구 제외되는데, **재시도 버튼은 `_SyncPendingBanner` 안에만 있으므로 노출되지 않는다** → F-5가 만든 유일한 탈출구가 이 조합에서만 닫힌다.

**왜 지금 문제인가**: 주석의 근거("검토 대상 기록은 업로드가 끝났다는 뜻")는 G-4 **이전**에는 참이었다(플래그 채택과 `synced` 승격이 같은 문장이었다). G-4가 그 둘을 분리하면서 근거가 거짓이 됐고, 배타 규칙만 남았다.

**빈도**: 낮다(인플라이트 편집 ∧ 서버 플래그). 하지만 걸리면 사용자가 스스로 벗어날 수 없다.

**고칠 곳 · 방법** (택1, 수정은 하지 않았다)

- (권장) `run_detail_page.dart:357`의 플래그 분기를 배타로 두되, 그 안에서 `retryExhausted && isSyncPending(record, syncStatus: syncStatus)`일 때 **재시도 액션만** 함께 노출한다. 배너를 2개로 늘리지 않으므로 ARCHITECTURE의 "세 번째를 추가하지 않는다" 방침과 충돌하지 않는다.
- (최소) 최소한 `:354-356` 주석을 사실에 맞게 갱신하고(“G-4 이후 flagged+pending이 성립한다”), TRD §14 #29 ③에 이 조합을 명시한다. 지금 상태는 **코드가 문서보다 앞서 있고 주석이 뒤에 남은** 전형적 케이스다.

## PLAUSIBLE-1 — `_fromRemote`의 jsonb 문자열 방어가 `samples`에만 있다

**파일**: `lib/features/tracking/data/local_run_repository.dart:712-717`

`samples`에 대해서는 "PostgREST가 jsonb를 문자열로 돌려주는 드문 경우 방어"가 들어 있는데, 같은 성질의 컬럼인 `client_reported`에는 없다. 그 경우 `_$RunRecordFromJson`(`run_record.g.dart:70`)의 `json['client_reported'] as Map<String, dynamic>`이 캐스트 예외를 던지고, `findById`의 원격 경로 전체가 실패한다(`guardSupabase`가 삼키면 상세 화면이 조용히 빈다).

같은 위험이 `applyServerConfirmation` 경로에도 있다 — 문자열을 그대로 `summaryJson`에 넣으면 다음 `runRecordFromRow`에서 터진다.

**PLAUSIBLE로 두는 이유**: 그 방어 주석 자체가 "드문 경우"라고 적고 있고, 이번 라운드에서 재현하지 못했다(UNVERIFIED-1과 같은 이유 — non-null 행이 0건). 방어를 넣는다면 `_fromRemote`의 `samples` 분기 바로 아래에 대칭으로 한 줄이면 된다.

## PLAUSIBLE-2 — `max_speed_mps`를 되받지 않아 "조정 전/후"가 같은 값이 된다 (선행 이슈, 이번 라운드 신규 아님)

`_adoptedKeys`에 `max_speed_mps`가 없다(`_serverAdjustedKeys` = `distance_meters` · `moving_seconds`뿐, :175). 그런데 서버는 거리를 채택할 때 `new.max_speed_mps := coalesce(v_recalc.max_speed_mps, ...)`로 이 값도 **재계산해 덮어쓴다**(마이그레이션 64:391).

결과: 로컬 `record.maxSpeedMps`는 재계산 **전** 주장값 그대로이고, 새로 되받은 `record.clientReported!.maxSpeedMps`도 **같은 재계산 전 값**이다. 즉 두 값이 항상 같아 "조정 전/후"로 쓸 수 없고, 서버와는 어긋난다.

지금 `maxSpeedMps`를 읽는 UI가 없어(`run_session_aggregator.dart`가 쓰기만 한다) 무해하지만, 최고속도를 뱃지·PB·공유 카드에 쓰기 시작하는 순간 거리와 똑같은 divergence가 재발한다. `_serverAdjustedKeys`에 한 줄 추가하면 닫힌다.

## PLAUSIBLE-3 — `watchSyncRetryExhausted`에 `status == completed` 필터가 없다

`local_run_repository.dart:433-436`은 id + `sync_status != synced` + `syncAttempts >= max`만 본다. `syncPending`(:454)은 여기에 더해 `status == completed`를 요구한다. `recording`/`paused` 체크포인트 행은 `_push` 대상이 아니라 `syncAttempts`가 오르지 않으므로 실무상 도달 불가지만, 두 술어를 "정확히 상보"라고 주석에 적어 둔 이상 필터도 맞춰 두는 편이 낫다(한 줄).
