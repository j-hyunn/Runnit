## 0. 이 문서의 성격

PRD §11이 명시한 대로 **GPS 현장 검증은 AI로 단축되지 않는 항목**이다. 자동 테스트
(합성 GPS 로그 기반 `test/tracking/gps_smoothing_test.dart` 등)는 알고리즘의 **논리**만
고정할 뿐, 실제 GNSS 노이즈·도심 멀티패스·OS 백그라운드 정책·기기별 배터리 정책은
재현하지 못한다. 이 문서는 **실기기를 들고 나가서 무엇을 어떻게 재고, 무엇을 합격으로
볼 것인가**를 정본화한다.

- 이 문서를 실행하는 주체는 사람이다. 각 항목은 그대로 체크리스트로 쓸 수 있게 썼다.
- 측정 결과는 §7 템플릿에 기록하고, 임계값을 바꾸게 되면 **`docs/TRD.md` §8.3 / §14**에
  반영한다(하네스 규칙 3: 문서와 코드가 벌어지지 않게 한다).
- PRD §11의 권장대로 **Phase 1 종료 시점 클로즈드 베타 직전**이 이 검증의 실행 시점이다.
  "거리가 정확한가, 배터리가 버티는가"가 이 앱의 최대 기술 리스크이기 때문이다.

## 1. 현재 구현 요약 — 검증 대상 파이프라인과 실제 파라미터

코드에서 인용한 **실제 값**이다. 문헌값이나 계획값이 아니다.

### 1.1 단계별 흐름

```
geolocator getPositionStream           ← lib/features/tracking/data/geolocator_run_tracking_service.dart
  → GpsTrackFilter.add()               ← lib/features/tracking/domain/gps_smoothing.dart
     ① 정확도 게이트 → ② 신호유실 감지 → ③ 이동평균 → ④ 점프 제거 → ⑤ 정지/이동 상태기계
  → RunSessionAggregator.addFix()      ← lib/features/tracking/domain/run_session_aggregator.dart
     거리·이동시간 누적 / 고도 / 칼로리 / 워치 심박 합류 → RunSample
  → 1초 틱 snapshot() → activeRunProvider (UI) / 15초 체크포인트 → drift 로컬 저장
  → stop() → LocalRunRepository.save() → 서버 upsert → validate_run 재검증
  → 랩 분할(표시용)                     ← lib/features/history/domain/lap_splits.dart
```

### 1.2 수집(TR-01/TR-04) — `geolocator_run_tracking_service.dart`

| 항목 | 값 | 위치 |
|---|---|---|
| 프로파일 기본값 | `TrackingProfile.standard` | `gps_smoothing.dart` `TrackingProfile` |
| fix 기대 간격 | highAccuracy 1s / **standard 5s** / batterySaver 10s | `expectedIntervalSeconds` |
| `distanceFilter` | 0m / **3m** / 8m | `distanceFilterMeters` |
| `LocationAccuracy` | best / **high** / medium | `_locationSettings()` |
| Android | `AndroidSettings(intervalDuration = 프로파일 간격)` + 포그라운드 서비스 알림 | 동 |
| iOS | `AppleSettings(activityType: fitness, pauseLocationUpdatesAutomatically: false, showBackgroundLocationIndicator: true)` | 동 |
| UI 틱 | 1초 `Timer.periodic` (거리 계산과 무관, 화면 갱신 전용) | `_tick()` |
| 크래시 대비 체크포인트 | **15초** (`checkpointInterval`) | 생성자 기본값 |

⚠️ **TR-04(5초 이내 최신 위치 반영)의 실제 상한은 프로파일이 정한다.** standard는 5초
간격이므로 이론 상한이 곧 수용 기준값과 같다. batterySaver(10초)에서는 **TR-04를 구조적으로
만족할 수 없다** — 이 사실을 §3.4에서 별도 판정 항목으로 둔다.

### 1.3 노이즈 필터·스무딩(TR-05) — `GpsFilterConfig` 기본값

| 파라미터 | 값 | 의미 |
|---|---|---|
| `maxAccuracyMeters` | **25** | 이보다 부정확한 fix는 통째로 폐기 |
| `maxPlausibleSpeedMps` | **8.5** (≈30.6 km/h) | 구간 속도 초과 시 점프로 보고 폐기 + 이동평균 창에서도 제거 |
| `minMovingSpeedMps` | **0.6** (≈2.2 km/h) | 이동 중 이 미만 구간은 미누적 |
| `minStepMeters` | **1.0** | 노이즈 바닥값 하한 |
| `smoothingWindow` | **5** | 최근 5개 좌표 단순 이동평균 |
| `signalGapSeconds` | **20** | 초과 시 이동평균 창·정지판정 창 리셋 |
| `maxBridgeSeconds` | **120** | 초과 공백은 잇지 않고 정지 상태로 재시작 |
| `stationaryExitMeters` | **8** (실효 `max(8, 정확도×1.5)`) | 정지 탈출 순 변위 |
| `stationaryEnterMeters` | **6** (실효 `max(6, 정확도)`) | 정지 복귀 순 변위(히스테리시스) |
| `stopWindowSeconds` | **10** (실효 `max(10, 간격×2.5)` → standard에서 **12.5초**) | 정지 복귀 관측 창 |
| `stationaryAnchorEma` | **0.1** | 정지 중 anchor 추종 계수 |
| 이동 노이즈 바닥값 | `max(1.0, min(정확도×0.35, 간격×0.6×0.5))` | `_noiseFloor()` |
| 거리 공식 | Haversine (지구 반경 6,371,008.8m) | `haversineMeters()` |

⚠️ **문서 ↔ 코드 불일치(현장 검증 전 인지해 둘 것).** `docs/TRD.md` §8.3은
"`accuracy > 20m` 제외 / 순간 속도 25km/h 초과 제거"로 적혀 있으나 코드는 **25m / 30.6km/h**다.
현장 측정으로 어느 쪽이 맞는지 정한 뒤 **TRD를 코드에 맞추거나 코드를 TRD에 맞춘다**
(§8 후속조치 후보 C-1).

### 1.4 거리·이동시간 누적(TR-01/TR-03) — 상태기계

- 세션은 **항상 `stationary`로 시작**한다(출발선 대기 시간이 거리가 되지 않게).
- `stationary` 중에는 거리를 **1m도 누적하지 않고**, 탈출 순간 anchor→현재 순 변위를
  통째로 한 번 더한다(시작 구간 손실 방지).
- `moving` 중에는 스무딩 좌표 간 구간 누적. 구간 속도 < 0.6 m/s 또는 이동량 < 노이즈
  바닥값이면 그 구간만 버린다.
- `movingSeconds`는 이동 인정 구간의 합이며 한 구간의 최대 기여는 `signalGapSeconds`(20초)다.
- `snapshot()`에서 `movingSeconds = min(moving, elapsed)`로 한 번 더 조인다
  (서버 `moving_exceeds_elapsed` 플래그 회피).

### 1.5 페이스·랩(TR-07)

- 실시간 평균 페이스 = `movingSeconds / (distanceMeters/1000)` — **분모가 movingSeconds**다
  (`run_session_aggregator.dart` `snapshot()`). 정지 시간을 넣으면 신호등 하나에 페이스가 무너진다.
- 랩(1km)은 완결 기록에서 `lib/features/history/domain/lap_splits.dart`가 계산한다.
  - `fullLapMeters = 1000`, `minSplittableMeters = 100`, `minPartialLapMeters = 50`
  - km 경계는 **누적거리 비율 선형 보간**(서버 `_run_km_split_seconds`와 같은 규칙)
  - 마지막 자투리 구간은 서버와 달리 `isPartial`로 함께 표시한다(의도적 차이)

### 1.6 칼로리(TR-06) — ACSM 러닝 대사 방정식

`run_session_aggregator.dart` `_kcalForSegment()`:

```
VO2(ml/kg/min) = 0.2 × 속도(m/min) + 3.5
MET            = VO2 / 3.5
kcal/min       = MET × 3.5 × 체중(kg) / 200
```

- 체중은 프로필 주입값, 없으면 **`_defaultWeightKg = 65`**.
- **이동 구간(`isMoving == true`)에만** 가산하며 한 구간의 시간 기여는 최대 60초로 클램프.
- 고도 데드밴드 `_elevationDeadbandMeters = 3.0` (GPS 고도는 수평보다 2~3배 부정확).

### 1.7 자동 일시정지(TR-03) — ⚠️ 현재 구현의 실체

**"15초 정지 시 `RunStatus.paused`로 전환"하는 코드는 없다.** 대신 상태기계가
`isStationary`로 전환되어 **거리·이동시간 누적을 멈춘다**. 관측 창은 standard 프로파일에서
**12.5초**이고, 그 창의 순 변위가 `max(6m, 정확도)` 미만이면 정지로 판정한다.

- 사용자 체감 결과(거리·페이스가 신호등에서 오염되지 않음)는 TR-03의 의도와 같다.
- 그러나 **UI에 "자동 일시정지됨" 표시가 없고**, `elapsedSeconds`(벽시계)는 계속 흐른다.
- `GpsTrackFilter.isStationary` getter는 존재하지만 **presentation 계층에서 소비하지 않는다**
  (`tracking_page.dart`에 참조 0건).

→ 현장 검증에서는 **"거리가 늘지 않는가"를 합격 기준으로 삼고**, UI 표시 부재는
§8 후속조치 후보(C-2)로 분리한다. 수용 기준 문구("정지 15초 감지")와 구현(12.5초 창)의
관계도 §3.3에서 실측으로 확인한다.

### 1.8 백그라운드 유지(TR-02)

- **Android**: geolocator `foregroundNotificationConfig`(제목 "Runnit 러닝 기록 중",
  `enableWakeLock: true`, `setOngoing: true`). **`_hasBackgroundPermission == true`일 때만 설정**된다.
  `flutter_background_service`는 의존성만 있고 **사용하지 않는다**(위치 스트림 이원화 방지).
- **iOS**: `UIBackgroundModes = [location]` + `allowBackgroundLocationUpdates = _hasBackgroundPermission`,
  `pauseLocationUpdatesAutomatically: false`.
- 권한 흐름(`ensureReady()`): 위치 서비스 확인 → `locationWhenInUse` 요청(거부 시 실패) →
  `locationAlways` 승격 요청(**거부해도 던지지 않음** → 포그라운드 전용 저하).

### 1.9 오프라인 동기화(TR-08)

- 완료 기록은 로컬(drift) 우선 저장 후 서버 upsert. id는 클라이언트 UUID v4라 **멱등**.
- 실패분 재시도 시점(`lib/core/sync/run_sync_coordinator.dart`): ① 로그인 성공,
  ② 앱 포그라운드 복귀, ③ **2분 주기 폴백**. 네트워크 복구 즉시 감지는 하지 않는다.
- 업로드 응답에서 서버 소유 컬럼(`is_flagged` 등)만 되받아 로컬에 겹쳐 쓴다
  (`_workspace/20260826_121500_gps_run-push-select.md`).

## 3. 수용 기준별 현장 테스트 프로토콜

### 3.1 TR-01 — 1km 실측 대비 오차 ±3% 이내 🔴 최우선

**참값(기준거리) 확보 방법 — 우선순위 순**

| 순위 | 방법 | 기준거리 | 장단점 |
|---|---|---|---|
| A | **공인 400m 트랙 1레인** ×N바퀴 | 400m × N (1레인 안쪽 30cm 기준 400.0m) | 참값 신뢰도 최고. **레인을 반드시 고정**할 것(2레인은 약 407m) |
| B | 트랙 2.5바퀴 = 1,000m | 1,000m | 단일 1km 측정의 기본형 |
| C | 지자체 표지 있는 하천변 코스(1km 마커) | 1,000m 단위 | 마커 정확도가 지자체마다 다름 — A/B로 보정 후 사용 |
| D | 대조군 앱 동시 기록 | 상대 비교 | 참값이 아니다. **보조 지표로만** 사용 |

**측정 프로토콜**

1. 트랙 출발선에서 앱을 **먼저 켜고 30초 대기**한 뒤 출발한다(콜드 픽스 안정화 + 정지
   드리프트 확인을 겸한다).
2. 1레인 고정, **일정 페이스(6:00~6:30/km 권장)** 로 주행.
3. 코스별 세트:
   - **세트 A (기본)**: 2.5바퀴(1,000m) × **3회 반복**
   - **세트 B (거리 누적 오차)**: 12.5바퀴(5,000m) × **2회 반복** — 오차가 거리에 비례하는지
     상수인지 구분하기 위함
   - **세트 C (도심)**: 고층 빌딩 사이 왕복 1km 코스 × 2회 — §3.5와 겸용
4. 각 회차마다 §7 표에 기록. **프로파일은 standard 고정**, 별도로 highAccuracy 1회를
   비교군으로 잰다.

**합격/불합격 기준**

| 판정 | 기준 |
|---|---|
| ✅ 합격 | 세트 A 3회 **전부** `|오차| ≤ 3.0%`, 그리고 3회 평균 `|오차| ≤ 2.0%` |
| ⚠️ 조건부 | 3회 중 1회만 3~5%. → 2회 추가 측정, 5회 중 4회 이상 3% 이내면 합격 |
| ❌ 불합격 | 3% 초과가 2회 이상, 또는 **부호가 한쪽으로 몰림**(체계적 편향) |

⚠️ **부호를 반드시 기록한다.** 계속 과소 측정(-)이면 정지 상태기계가 실제 이동을 잘라내고
있다는 뜻(→ `stationaryExitMeters` / `minMovingSpeedMps` 하향 검토), 계속 과대(+)면
스무딩 부족 또는 코너링 오차(→ `smoothingWindow` 상향 검토)다. 세트 B에서 오차%가
세트 A보다 **커지면** 누적성 편향이고, 비슷하면 시작·종료 구간의 상수 오차다.

### 3.2 TR-02 — 60분 연속 기록, 데이터 손실 0

**시나리오(한 번의 60분 러닝 안에서 순서대로 수행, 각 구간 시각을 수기로 기록)**

| 구간 | 시각(분) | 행동 |
|---|---|---|
| S1 | 0–10 | 앱 화면 켜둔 채 주행(기준 구간) |
| S2 | 10–20 | **화면 잠금**(전원 버튼) 후 주행 |
| S3 | 20–30 | 다른 앱(지도/음악/카톡) 전환 후 주행 |
| S4 | 30–35 | 카메라 앱 실행 후 사진 2장 촬영(메모리 압박 유발) |
| S5 | 35–45 | 화면 잠금 + 주머니 보관 |
| S6 | 45–55 | 음악 스트리밍 재생 중 화면 잠금 |
| S7 | 55–60 | 앱 복귀 후 주행 → 종료 |

**합격 기준**

- 종료 후 상세 화면에서 **경로 폴리라인에 끊김(직선 점프)이 없을 것.**
- 랩 테이블에 1km 랩이 전부 존재하고, **특정 랩의 페이스만 비정상적으로 느리지 않을 것**
  (그 구간이 통째로 유실됐다는 신호다).
- 전체 거리 오차가 §3.1 기준 안(±3%).
- `samples` 개수 ≥ `60분 ÷ 5초 × 0.9` = **648개 이상**(standard 프로파일 기준, 10% 손실 허용).
  Supabase에서 `select jsonb_array_length(samples) from runs where id = '...'`로 확인.
- 구간별 판정: S2~S6 각 10분 구간의 샘플 수가 S1(기준 구간) 대비 **80% 이상**.
  어느 한 구간만 급감하면 그 OS 동작이 원인이다.
- 앱이 재시작되지 않았을 것(재시작 시 `interruptedRunProvider` 복구 배너가 뜬다 → 실패 신호).

⚠️ **Android는 제조사별로 따로 잰다.** 삼성(One UI)·샤오미(MIUI)·화웨이는 포그라운드
서비스를 자체 정책으로 죽인 전례가 있다. §5 기기 매트릭스 참조.

### 3.3 TR-03 — 정지 15초 자동 일시정지

**시나리오**

| # | 상황 | 방법 | 기대 |
|---|---|---|---|
| A-1 | 신호대기 | 횡단보도 앞 **60초 정지** ×3회 | 정지 시작 후 ~12.5초 이내 거리 증가 중단, 60초 동안 누적 증가 **< 5m** |
| A-2 | 짧은 정지 | 20초 정지 ×3회 | 동일. 재출발 시 누락 없이 이어짐 |
| A-3 | 오탈출 확인 | 도심 빌딩 사이에서 **3분 완전 정지** | 3분간 누적 증가 **< 10m** |
| A-4 | 재출발 반응 | 정지 후 출발 → 10m 지점 통과 시각 기록 | 출발 후 **5초 이내** 거리 증가 재개 |
| A-5 | 느린 걷기 오탐 | 3km/h로 200m 보행 | 이동으로 인정되어 누적될 것(잘라먹지 않을 것) |

**합격 기준**: A-1/A-2/A-3 전부 위 임계 이내 + A-4 5초 이내 + A-5 실측 200m 대비 오차 ±10% 이내.

**기록해 둘 것**: A-1에서 "거리 증가가 멈춘 시각 − 실제로 멈춘 시각"을 스톱워치로 잰다.
이 값이 **15초를 크게 넘으면** `stopWindowSeconds`를 낮추고, **5초 미만이면** 신호 대기가
아닌 감속 구간까지 잘라낼 위험이 있으므로 올린다. PRD 수용 기준의 "15초"와 실측 지연을
같은 표에 병기한다.

### 3.4 TR-04 — 5초 이내 최신 위치 반영

**방법**

1. 지도 화면을 보면서 **직선 100m 구간**을 일정 속도로 주행.
2. 명확한 랜드마크(전봇대·횡단보도 시작선) 3곳을 지날 때마다 **"통과!" 하고 화면을 촬영**
   하거나 동행자가 스톱워치를 찍는다.
3. 화면의 현재 위치 마커가 그 랜드마크에 도달하는 시각과의 차이를 잰다. 3지점 × 3회.

**합격 기준**

| 프로파일 | 기준 | 비고 |
|---|---|---|
| standard(기본) | 9회 중 8회 이상 **≤ 5초** | PRD TR-04 수용 기준 |
| highAccuracy | 9회 전부 ≤ 3초 | 참고값 |
| batterySaver | **판정 제외** | 10초 폴링이라 구조적으로 5초를 만족할 수 없다 → §8 C-3 |

⚠️ 이동평균 창(5)으로 스무딩 좌표는 실제 위치보다 **약 2 fix(= standard에서 10초)** 뒤처진다.
지도 마커가 `RunSample`(스무딩 좌표)을 그린다면 **이 지연이 그대로 체감된다.** 측정에서
5초를 넘으면 원인이 폴링 주기인지 스무딩 지연인지 구분해 기록할 것(§8 C-4).

### 3.5 TR-05 — 비현실적 점프 제거

**재현 위치 예시(서울 기준. 지역에 맞게 동등 조건으로 치환 가능)**

| 유형 | 예시 장소 | 확인 대상 |
|---|---|---|
| 터널·지하차도 | 남산 1호터널 보행로 / 여의도 지하보도 / 한강 하부 통로 | 진입~복귀 구간에 직선 점프가 생기지 않는가 |
| 고층 캐니언 | 여의도 IFC~파크원 사이, 강남역 테헤란로, 종로 청진동 | 좌표가 건물 위로 튀어 폴리라인이 톱니가 되지 않는가 |
| 교량 하부 | 한강 다리 밑 자전거도로(원효대교·마포대교 하부) | 정확도 급락 시 fix 폐기가 동작하는가 |
| 하천 복개·둔치 | 청계천 복개 구간, 양재천 지하통로 | 짧은(<20초) 공백의 이어붙임 |
| 실내 진입 | 대형 지하주차장 진입로 | 정확도 게이트(25m)가 걸리는가 |

**방법**: 위 유형 중 최소 3종에서 각 1회 이상 통과하는 **총 5km 이상 도심 코스**를 1회 주행.

**합격 기준**

- 상세 화면 지도에서 **경로 밖(도로/보도 이탈) 50m 초과의 스파이크가 0건**.
- 랩 페이스에 **3:00/km 미만 또는 12:00/km 초과의 비현실적 랩이 없을 것**(정지 제외).
- `RunRecord.maxSpeedMps` ≤ 8.5 (필터 상한. 초과하면 필터를 통과했다는 뜻 → 결함).
- 서버 `is_flagged`가 `null`일 것(`implausible_*` 플래그가 붙으면 불합격).
- 도심 코스의 총거리 오차가 §3.1 A(트랙)의 오차보다 **2배 이상 나빠지지 않을 것**.

⚠️ **함께 확인할 실패 모드**: 정확도 게이트(25m)가 도심에서 fix를 과도하게 버려 **거리가
과소 측정**되는 현상. 도심 오차 부호가 계속 (−)면 게이트가 원인일 가능성이 높다.

### 3.6 TR-06 — 칼로리 추정

**케이스(같은 러너가 아니어도 되지만, 체중은 프로필에 정확히 입력한 상태로)**

| # | 체중 | 거리 | 목표 페이스 | 산식 기대치(ACSM, 이동시간 기준) |
|---|---|---|---|---|
| K-1 | 60kg | 5km | 6:00/km | 속도 2.78m/s → VO2 36.8 → MET 10.5 → **약 315 kcal** |
| K-2 | 60kg | 5km | 5:00/km | 3.33m/s → VO2 43.5 → MET 12.4 → **약 311 kcal** |
| K-3 | 80kg | 5km | 6:00/km | MET 10.5, 체중 80 → **약 420 kcal** |
| K-4 | 60kg | 10km | 6:00/km | K-1의 2배 → **약 630 kcal** |
| K-5 | 체중 미입력 | 5km | 6:00/km | 기본 65kg로 계산 → 약 341 kcal |

> 위 기대치는 §1.6 산식을 그대로 적용한 값이다. 실측값이 이 계산과 **±5% 이내**면 산식이
> 코드에 올바르게 구현된 것이다(구현 검증). 그 다음이 타 앱 대조(타당성 검증)다.

**합격 기준**

| 층위 | 기준 |
|---|---|
| 산식 구현 정합 | 실측 kcal이 위 기대치 대비 **±5% 이내** |
| 타 앱 대조 | 동일 러닝의 나이키런/스트라바/애플 피트니스 값 대비 **±20% 이내** |
| 체중 반영 | K-1 vs K-3에서 kcal 비율이 체중 비율(80/60 = 1.33)과 **±5% 이내로 일치** |
| 거리 반영 | K-4 ≈ K-1 × 2 (±10%) |
| 페이스 영향 | K-1과 K-2의 차이가 **10% 이내**일 것(ACSM 산식상 총 kcal은 페이스에 크게 의존하지 않는다 — 사용자에게 "왜 빨리 뛰었는데 칼로리가 같냐"는 문의가 올 수 있으므로 **UI 문구 검토 항목**으로 남긴다) |

⚠️ 심박 기반 정교화는 P1(WR-05)이다. 이번 검증에서는 **ACSM 추정치임을 UI가 밝히는지**까지만 본다.

### 3.7 TR-07 — 1km 랩

- §3.1 세트 B(5km)에서 랩 테이블을 확인한다.
- 합격: 랩 5개 + 자투리(`isPartial`) 표기가 정확하고, **각 랩 합계 ≈ 총 이동시간**(±3초),
  각 랩 거리 = 1,000m.
- 트랙 세트 B에서는 실제 랩 타임을 스톱워치로 재서 **랩당 오차 ±5초 이내**를 확인한다.
- 서버 재계산 랩(`_run_km_split_seconds`)과 클라이언트 랩이 **같은 값인지** 1건 대조한다.

### 3.8 TR-08 — 완전 무신호 구간 + 오프라인 동기화

TR-08의 PRD 수용 기준은 "네트워크 없이 기록 후 100% 업로드"다. 여기에 지시서가 요구한
**GPS 완전 무신호 구간 진입/복귀**를 함께 묶는다(두 현상은 지하에서 동시에 발생한다).

| # | 시나리오 | 방법 | 합격 기준 |
|---|---|---|---|
| N-1 | 지하상가 통과(짧음) | 지하도 60초 통과 후 지상 복귀 | 공백 < 120초이므로 이어붙임. 진입~복귀 직선거리와 누적 증가분의 차 **≤ 30m**. 폴리라인에 지상 지물 관통 스파이크 없음 |
| N-2 | 지하철 승강장(김) | 지하 3분 이상 체류 후 지상 복귀 | 공백 > `maxBridgeSeconds`(120s) → **이어붙이지 않고** 정지 상태로 재시작. 이동하지 않은 거리가 더해지지 않을 것 |
| N-3 | 지하철 탑승(이동) | 한 정거장 탑승 후 하차·재개 | **역간 거리가 러닝 거리로 더해지지 않을 것** ← 랭킹 신뢰의 핵심. 서버 `is_flagged`도 확인 |
| N-4 | 기내모드 러닝 | 시작 전 기내모드 ON → 3km 주행 → 종료 → 앱 유지 | 종료 화면 정상. 로컬 저장 성공 |
| N-5 | 오프라인 복귀 | N-4 후 기내모드 OFF | **2분 이내** 자동 업로드(폴백 주기). 실패 시 앱을 백그라운드↔포그라운드 전환하면 즉시 재시도되는지 확인 |
| N-6 | 오프라인 다건 | 기내모드로 러닝 2건 기록 후 온라인 복귀 | 2건 모두 업로드, 중복 행 없음(UUID 멱등) |
| N-7 | 앱 강제 종료 | 러닝 20분 시점에 앱 강제 종료 → 재실행 | 복구 배너로 미완결 세션 제시, **최대 손실 15초**(체크포인트 주기) |

**합격 기준(전체)**: N-1~N-7 전부 통과 + Supabase `runs` 테이블에 정확히 예상 건수만 존재.

## 4. 배터리 소모 측정 프로토콜 (Phase 3 항목 · 같은 러닝에서 병행)

PRD §6: **1시간 러닝 트래킹 시 배터리 소모 10% 이하.**

**측정 조건 통제(이걸 안 맞추면 숫자에 의미가 없다)**

| 항목 | 고정값 |
|---|---|
| 시작 배터리 | 80~100% (저전력 모드 자동 진입 구간 회피) |
| 저전력 모드 | **OFF** (iOS 저전력 절전, Android 절전 모드 모두 OFF) |
| 화면 | 잠금 상태 유지(§3.2 S5와 동일 조건). 화면 ON 조건은 별도 행으로 측정 |
| 밝기 | 50% 고정, 자동 밝기 OFF |
| 네트워크 | LTE/5G 유지(Wi-Fi OFF) — 실제 러닝 조건 |
| 동시 실행 | 음악 스트리밍 OFF 조건과 ON 조건을 따로 측정 |
| 온도 | 영상 10~25℃. 혹한/혹서는 별도 비고 |
| 기록 방법 | 시작·종료 시각의 배터리 % 수기 기록 + OS 배터리 사용 내역에서 Runnit 항목 확인 |

**측정 세트**

| 세트 | 프로파일 | 화면 | 음악 | 시간 | 합격 기준 |
|---|---|---|---|---|---|
| B-1 | standard | 잠금 | OFF | 60분 | **≤ 10%** 🔴 PRD 기준 |
| B-2 | standard | 상시 ON | OFF | 60분 | ≤ 20% (참고값. 화면이 지배적임을 확인) |
| B-3 | standard | 잠금 | ON | 60분 | ≤ 15% (참고값) |
| B-4 | batterySaver | 잠금 | OFF | 60분 | **≤ 7%** (절전 모드가 실제로 이득이 있는지) |
| B-5 | highAccuracy | 잠금 | OFF | 60분 | 참고값(상한 없음). B-1 대비 증가폭을 기록 |

- iOS·Android **각각** B-1은 필수, B-2~B-5는 가능한 범위에서.
- OS 배터리 내역에서 **Runnit 자체 소모 %** 와 **총 소모 %** 를 분리 기록한다
  (화면·셀룰러 소모가 섞이면 앱 탓으로 오판한다).
- ⚠️ B-4가 B-1과 차이가 없으면 절전 프로파일을 사용자에게 노출할 이유가 없다 →
  프로파일 설계 재검토 신호.

| W-3 | Garmin 착용 러닝 | 러닝 중에는 지표가 안 보이고, Garmin Connect 동기화 후 나타나는가 | `source = external`, `vendor = watchGarmin`, **UI에 "동기화 후 반영" 안내 노출** |
| W-4 | 워치 미연동 | 워치 없이 러닝 | **에러 없이** 폰 단독 진행(정상 경로) |
| W-5 | 권한 거부 | 건강 권한 거부 후 러닝 | 폴백, 러닝 중단되지 않음 |
| W-6 | **경로 있는 워치 기록** | Apple Watch/Garmin 야외 러닝을 앱으로 가져오기 | §5.7: 경로 샘플 존재 → **티어·랭킹 반영** |
| W-7 | **경로 없는 워치 기록** | 워치 실내 러닝(거리만) 가져오기 | §5.7: 경로 없음 → **수동 기록으로 분류, 티어·랭킹 미반영** |
| W-8 | 중복 병합(WR-04) | 폰과 워치가 같은 시간대 기록 | 시간 겹침 감지 후 사용자 선택 |

⚠️ **W-6/W-7은 현재 서버 구현과 PRD의 판정 축이 다르다.** 서버는 티어·랭킹 제외를
`activity_type <> 'indoor_run'`으로 판정하고(마이그레이션 19/22/23), **경로 샘플 유무로
판정하지 않는다.** 폰 GPS만 있는 P0에서는 결과가 같지만, **워치 임포트가 붙는 순간
"경로 없는 outdoor_run"이 티어에 들어간다.** 임포트 경로 구현 전에 판정식을 §5.7에
맞춰야 한다 → §8 후속조치 후보 **C-5(중요)**.

## 8. 알려진 리스크와 "코드 후속조치 후보"

검증 계획을 세우면서 코드에서 실제로 확인한 사항들이다. **이번 작업에서는 수정하지 않았다.**

### 8.1 리스크 (검증 결과와 무관하게 이미 알고 있는 제약)

| # | 리스크 | 현재 코드 상태(확인함) | 현장 영향 |
|---|---|---|---|
| R-1 | **iOS 백그라운드가 "항상 허용"에 종속** | `ensureReady()`가 `locationAlways` 승격에 실패해도 던지지 않고 `_hasBackgroundPermission = false`. 이때 `allowBackgroundLocationUpdates`도 false | 사용자가 "앱 사용 중"만 허용하면 **TR-02가 구조적으로 불가능**. 검증 시 권한 상태를 반드시 기록할 것 |
| R-2 | **Android 배터리 최적화 예외 요청 경로가 없음** | `ignoreBatteryOptimizations` 관련 코드 **0건**(grep 확인) | 샤오미/화웨이/일부 삼성에서 포그라운드 서비스가 죽어 TR-02 실패 가능. 지금은 사용자가 설정에서 직접 켜는 수밖에 없다 |
| R-3 | **Android 포그라운드 알림이 "항상 허용" 여부에 묶여 있음** | `foregroundNotificationConfig`가 `_hasBackgroundPermission == true`일 때만 설정됨 | 의도된 설계지만, 권한 조합에 따라 **화면 잠금 즉시 기록이 멈추는 조합**이 존재한다. 검증 시 (whenInUse만 / always) 두 조건 모두 측정 |
| R-4 | **geolocator 설정의 한계** | Android `intervalDuration`은 요청일 뿐 OS가 보장하지 않음. iOS는 `distanceFilter`가 우선해 정지 시 콜백이 아예 안 올 수 있음 | 정지 판정 창이 fix 부재로 늦어질 수 있다 → §3.3 지연 실측이 중요 |
