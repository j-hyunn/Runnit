## 2. 마이그레이션 53 — `profiles.weekly_goal_km`

```sql
alter table public.profiles add column if not exists weekly_goal_km double precision;
alter table public.profiles add constraint profiles_weekly_goal_range
  check (weekly_goal_km is null or (weekly_goal_km > 0 and weekly_goal_km <= 500));
```

**결정 3건**

1. **타입은 `numeric`이 아니라 `double precision`.** TRD의 폐기된 §4 DDL 초안은 `numeric`으로
   적고 있으나, 실제 스키마에서 같은 화면에 함께 편집되는 `weight_kg`·`height_cm`가
   `double precision`이다. Dart는 어느 쪽이든 `double` 하나로 받으므로 타입을 섞을 이유가 없다.
2. **단위는 km** (컬럼명 `_km`가 표식). 프로젝트의 다른 거리 컬럼은 전부 m이므로 **이 컬럼만
   예외**다 — 사용자가 "주 30km"로 입력·인지하는 값이라 저장 단위를 입력 단위에 맞췄다.
   달성률(`total_distance_meters / 1000` 대비)은 클라이언트가 계산한다.
   **서버는 이 값으로 아무 판정도 하지 않는다** — 랭킹·티어·뱃지와 무관한 표시 전용.
3. **미설정은 `NULL`, 0이 아니다.** 상한 500km는 엘리트 러너 주간 주행거리(160~200km)를 크게
   웃돌아 정상 입력을 막지 않으면서 오타(3000)·단위 착각(30000)만 걸러낸다.

### ⚠️ 가드 트리거는 손대지 않았다 — 브리핑과 다른 점

브리핑은 "05 가드의 화이트리스트에 추가"를 지시했으나, **`trg_profiles_guard`는
화이트리스트가 아니라 블랙리스트다.** 05 → 19 → 39로 갱신된 현재 본문은 서버 전용 컬럼
(`total_*`/`level`/`current_tier`/`season_distance_meters`/`streak_*`/`crew_id`)을 `old` 값으로
**되돌릴 뿐**, 열거되지 않은 컬럼은 그대로 통과시킨다. `weight_kg`가 지금까지 편집 가능했던
것도 같은 이유다. 따라서 `weekly_goal_km`은 **컬럼 추가만으로 편집이 열린다.**

`runs` 가드(마이그레이션 51, §4.4)와 기본값이 정반대라는 점이 함정이라 문서에 표로 남겼다:

| | `runs` | `profiles` |
|---|---|---|
| 방식 | 화이트리스트 (`new := old` 후 `title`/`note`만 재적용) | 블랙리스트 (서버 전용 컬럼만 되돌림) |
| 신설 컬럼 기본값 | 자동 보호됨 | **자동 편집 가능** |
| 주의 | 편집 컬럼 늘리려면 가드 수정 | **서버 전용 컬럼 만들면 반드시 가드 등록** |

## 3. 마이그레이션 54 — `avatars` Storage

| 항목 | 값 |
|---|---|
| 버킷 | `avatars`, `public = true` |
| **경로 규약** | **`avatars/{auth.uid()}/{filename}`** — 첫 폴더 세그먼트가 곧 쓰기 권한 술어 |
| 제한 | 2 MiB, `image/jpeg`·`image/png`·`image/webp` — **버킷 설정**으로 강제 |
| `avatars_select_public` | `to anon, authenticated using (bucket_id = 'avatars')` |
| `avatars_insert_own` | `with check (bucket_id='avatars' and (storage.foldername(name))[1] = (select auth.uid())::text)` |
| `avatars_update_own` | 위 술어를 `using` + `with check` **양쪽에** |
| `avatars_delete_own` | 위 술어를 `using`에 |

**결정 근거**

- **public 버킷인 이유**: AC-03 타인 프로필과 랭킹 리스트가 남의 아바타를 그리고, 게스트
  모드(마이그레이션 17)에서도 global 랭킹의 `avatar_url`이 보인다. 서명 URL로 하면 랭킹
  한 페이지마다 N개 서명을 발급해야 하는데, 아바타는 애초에 전원에게 공개되는 정보다.
- **용량·확장자를 RLS가 아니라 버킷 설정으로 건 이유**: RLS 술어는 업로드 바이트 수를 알 수
  없다(`metadata`는 업로드 **완료 후** 채워진다). storage API는 `file_size_limit` /
  `allowed_mime_types`를 업로드 **전에** 거절한다.
- **update에 `using`과 `with check`를 둘 다 건 이유**: `using`만 걸면 "남의 파일을 내 폴더로
  rename"이, `with check`만 걸면 "내 폴더로 옮겨오기"가 열린다.

**클라이언트 계약 (ui 담당에게)**

- 같은 경로 덮어쓰기 금지. **타임스탬프 파일명으로 새 경로 업로드 → `profiles.avatar_url`
  갱신 → 이전 파일 delete** 순서. 덮어쓰기는 CDN/이미지 캐시 때문에 앱에 옛 사진이 남는다.
- 업로드 전 장변 512px 리사이즈 권장(2 MiB 상한을 UI에서 미리 만족시킨다).
- 경로 규약을 어기면 업로드가 `42501`로 거절된다.

**미해결로 남긴 것**: AC-04(계정 삭제) 시 `auth.users` 삭제가 `storage.objects`를 cascade 하지
않는다 → 고아 아바타 파일 정리 경로가 필요하다. AC-04 작업 시 함께 처리.

## 4. 마이그레이션 55 — `user_badges` 공개 SELECT

### 🛑 작업 중 발견: 스키마 드리프트

`get_advisors(performance)`가 존재하지도 않아야 할 정책명을 언급해 확인해 봤다.

```
public.user_badges  user_badges_select_public  {authenticated}  SELECT
  (user_id <> (select auth.uid())) and (revoked = false) and (verified = true)
```

**원격 DB(`xwtbwexcofcgmbvktwdo`)에는 이 정책이 이미 존재한다.** 그런데
`supabase_migrations.schema_migrations`의 마지막 이력은 `20260831070924 / 52_...`이고,
`user_badges_select_public`은 **마이그레이션 파일 어디에도 없다.** 대시보드나 임시 SQL로
마이그레이션 밖에서 만들어진 정책이다.

- 지금까지의 실제 상태: **원격만 맞고, `supabase db reset`·스테이징·브랜치 DB는 틀리다.**
  그 환경에서만 AC-03 뱃지 갤러리가 조용히 0건이 된다.
- TRD §5 / ARCHITECTURE §5.5는 "타인은 `revoked=false and verified=true`만"이라고 이미
  적고 있었다 — 문서는 라이브를 기술했고 파일만 빠져 있었던 셈이다.

**조치**: 55가 라이브 술어를 **한 글자도 다르지 않게** 파일화한다. `drop policy if exists`로
감싸 멱등이며, 따라서 **원격 적용은 진짜 no-op**(동작 변화 0)이고 새 환경은 같은 값으로 수렴한다.

`user_id <> auth.uid()` 조건은 라이브 원본을 그대로 유지했다 — 본인 행은
`user_badges_select_own`이 이미 통과시키므로 두 정책의 대상을 서로소로 만들어 중복 평가를 줄인다.
결과 집합은 어느 형태든 동일하다(정책은 OR).

### 판단: 노출 컬럼

- `is_seen` — "축하 팝업을 봤는가". 민감정보 아님. 타인이 알아도 아무 일도 없다.
- `source_run_id` — 뱃지를 만든 러닝의 uuid. **`runs`는 `runs_select_own` 그대로**이므로
  uuid를 알아도 그 러닝 내용은 조회되지 않는다. 확정 사항("최근 러닝 목록 노출 안 함")이
  RLS로 그대로 강제된다. **`runs` RLS는 이번 작업에서 한 줄도 건드리지 않았다.**
- 컬럼 제한 뷰는 채택하지 않았다 — 본인/타인 경로마다 다른 소스를 쓰게 되어 클라이언트
  모델이 갈라진다. 위 두 컬럼 중 하나라도 민감해지면 그때 뷰로 좁힌다.

### 인덱스: 추가 없음

마이그레이션 25가 **이 정책 술어와 동일 조건**의 부분 인덱스를 이미 만들어 뒀다
(당시엔 정책 없이 인덱스만 선행 생성된 상태였다):
`user_badges_public_idx (user_id, earned_at desc) where revoked = false and verified = true`.
본인 갤러리는 `user_badges_user_earned_idx`가 커버한다.

### ⚠️ Realtime 부수효과 (qa/ui 확인 요망)

`user_badges`는 `supabase_realtime` publication에 들어 있고(07_rls.sql), Realtime은 구독자의
RLS로 이벤트 가시성을 판정한다. 이 정책이 있는 한 **타인의 뱃지 발급 이벤트도 구독자에게
도달**한다.

- 현재 코드는 안전하다 — `supabase_gamification_repository.dart`의 `watchUnseenBadges()`가
  이미 `PostgresChangeFilter(eq, 'user_id', userId)`로 좁혀 두었다.
- 다만 그 필터는 지금까지 "RLS가 어차피 막아주는데 덤으로"였던 것이 이제 **유일한 방어선**이
  된다. `user_badges`를 구독하는 코드를 새로 만들 때 `user_id` 필터를 빼면 남이 뱃지를 딸
  때마다 전 사용자가 재조회한다. 서버에서 막을 수 없다(정책을 좁히면 AC-03이 깨진다).

## 5. camelCase ↔ snake_case 매핑 (mobile-architect 확인 요망)

| Dart | Postgres | 타입 | 비고 |
|---|---|---|---|
| `AppUser.weeklyGoalKm` | `profiles.weekly_goal_km` | `double precision` nullable → Dart `double?` | **단위 km**. `NULL` = 미설정 |
| `AppUser.displayName` | `profiles.display_name` | text nullable | 기존 |
| `AppUser.avatarUrl` | `profiles.avatar_url` | text nullable | 기존. 여기에 Storage public URL을 넣는다 |
| `AppUser.weightKg` | `profiles.weight_kg` | double precision nullable | 기존 |

- `FieldRename.snake` 자동 변환으로 정확히 일치한다. 별칭(`as`) 사용 금지 규약 그대로.
- **`visibility` / `ProfileVisibility`는 만들지 않았다** — AC-05 삭제 확정(사용자).
- 클라이언트 검증도 CHECK와 같은 범위(`0 < x <= 500`)로 걸어 서버 400을 UI에서 미리 막는다.
