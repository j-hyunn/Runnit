## 1. 모델 변경

### 1.1 `AppUser.weeklyGoalKm` 신설 (`lib/models/app_user.dart`)

```dart
double? weeklyGoalKm,
```

- 위치: `preferredUnit` 바로 뒤. **사용자 편집 설정 블록**에 두고 서버 관리 통계
  캐시 블록(`totalDistanceMeters` 이하)과 분리했다. 이 파일에서 블록 경계가
  곧 "누가 쓰는 필드인가"의 경계이므로, 편집 가능한 값을 캐시 블록에 섞으면
  다음 사람이 가드 트리거 대상으로 오해한다.
- nullable(기본값 없음). `0`을 기본값으로 두면 "목표 0km"와 "목표 미설정"이
  구분되지 않아 UI가 진행률 0%를 보여줄지 위젯을 숨길지 정할 수 없다.
- **단위가 km다.** 다른 거리 필드가 전부 미터(`*Meters`)인 것과 의도적으로
  다르며, 이유는 사용자가 직접 입력·확인하는 표시값이기 때문이다. TRD §4.1에
  이 예외를 명시해 두었다.
- 코드 주석에 혼동 금지 대상 2개를 못 박았다:
  - **GM-05 주간 스트릭** — "주 N회 뛰었는가"의 서버 관리 캐시
    (`profiles.current_streak_weeks` 등). 이 필드는 스트릭 판정 입력이 아니다.
  - **TR-11 러닝별 목표** — 세션 시작 전에 잡는 일회성 목표. 프로필에 저장 안 함.
  - 티어·랭킹·뱃지 판정에도 어떤 형태로도 들어가지 않는다.

freezed/json 재생성 완료 — `app_user.g.dart`에 `weekly_goal_km` ↔ `weeklyGoalKm`
매핑이 정상 생성됐다(클래스가 `@JsonSerializable(fieldRename: FieldRename.snake)`).

### 1.2 `SeasonHistory.bestTierOf(...)` static 추가 (`lib/models/season_history.dart`)

TI-09 역대 최고 티어 판정 규칙(끝난 시즌만 / `isVoided` 제외 / `Tier.order` 최대)을
모델의 static으로 올렸다. 기존 `bestEverTierProvider`(본인)와 신설
`bestTierOfProvider`(타인)가 **같은 함수**를 부른다.

이유: 규칙을 provider마다 복제하면 "무효 시즌 제외" 같은 정책이 한쪽에만
반영되는 사고가 난다. `bestEverTierProvider`는 이 함수를 호출하도록 축약했고,
동작·의미는 그대로다(회귀 없음).

### 1.3 `visibility` — 추가하지 않음

AC-05 삭제 확정에 따라 `AppUser`에 `visibility` 필드도, `ProfileVisibility`
enum도 만들지 않았다. TRD §3.3 레거시 블록과 §4 보존 DDL 블록에 아직
`visibility` 서술이 남아 있으나 **그 정리는 orchestrator 담당**이라 손대지
않았다(브리핑 §AC-05).

## 2. 리포지토리 계층

### 2.1 `UserRepository.findById` — 시그니처 변경 없음, 계약만 명문화

```dart
Future<AppUser?> findById(String userId);
```

이미 존재하고 임의 id를 받는다. `profiles`가 전원 공개 SELECT
(`profiles_select_all`)이므로 **타인 조회용 메서드를 새로 만들 필요가 없다.**

의도적으로 하지 않은 것: "공개 필드만 담은 축소 모델(`PublicProfile`)"을
만들지 않았다. 만들면 `select()`에 컬럼 목록을 써야 하는데, 이 리포지토리의
기존 계약이 **"`select()`에 컬럼 별칭·목록을 쓰지 않는다"**(파일 상단 주석)이고
컬럼을 골라내는 순간 `AppUser.fromJson`이 required 필드를 잃고 깨진다.
따라서 **모델은 전체를 받고, "무엇을 보여줄지"는 표현 계층이 결정**한다.
`weightKg`/`heightCm`/`birthDate`/`weeklyGoalKm`는 타인 화면에서 렌더링하지
않는다 — 이 경계는 UI 담당이 지킨다.

### 2.2 `updateProfile` 편집 화이트리스트에 `weekly_goal_km` 추가

`SupabaseUserRepository._editablePatch`에 한 줄 추가:

```dart
'weekly_goal_km': user.weeklyGoalKm,
```

가드 트리거 관련(초기 추정 정정): `trg_profiles_guard`는 화이트리스트가 아니라
**블랙리스트**다 — 서버 전용 컬럼(`total_*`/`level`/`current_tier`/`streak_*`)만
`old` 값으로 되돌리고, 열거되지 않은 컬럼은 통과시킨다(마이그레이션 39 확인).
따라서 `weekly_goal_km`는 컬럼 추가만으로 편집이 열리며 가드 수정이 필요 없다.
**역방향 주의**: 앞으로 추가되는 컬럼은 기본이 "사용자 편집 가능"이므로,
서버 전용 컬럼을 만들 때 가드 등록을 빠뜨리면 클라이언트가 통계를 위조할 수 있다.

### 2.3 신규 리포지토리 메서드 — 없음

`GamificationRepository.fetchUserBadges(String userId)`는 이미 임의 id를 받고
`revoked = false`를 거른다. `SeasonHistoryRepository.fetchByUser(String userId)`도
동일. **타인 조회를 위해 새로 정의할 Dart 인터페이스는 하나도 없다.**
필요한 건 서버 쪽 RLS뿐이다(§4).

## 3. Provider 트리

신규 파일: **`lib/features/profile/data/other_profile_providers.dart`**

```
userProfileProvider(userId)            FutureProvider.autoDispose.family<AppUser?, String>
  └─ userRepositoryProvider.findById(userId)

userBadgesByIdProvider(userId)         FutureProvider.autoDispose.family<List<UserBadge>, String>
  ├─ currentUserIdProvider == null → const []
  └─ gamificationRepositoryProvider.fetchUserBadges(userId)   // revoked=false, badge 임베드

userSeasonHistoriesProvider(userId)    FutureProvider.autoDispose.family<List<SeasonHistory>, String>
  ├─ currentUserIdProvider == null → const []
  └─ seasonHistoryRepositoryProvider.fetchByUser(userId)

bestTierOfProvider(userId)             Provider.autoDispose.family<Tier?, String>
  └─ userSeasonHistoriesProvider(userId) → SeasonHistory.bestTierOf(...)
```

### 왜 본인용과 분리했나

| | 본인 (`currentProfileProvider` 등) | 타인 (신규) |
|---|---|---|
| 키 | 인증 상태(`currentUserIdProvider`) | 라우트 파라미터 `/users/:id` |
| 수명 | 앱 전역 상시 | 화면 이탈 시 폐기(`autoDispose`) |
| 노출 | 진행률·미획득 뱃지·무효 시즌 포함 | 획득 뱃지 + 확정 티어만 |

1. **키가 다르다.** 본인용을 재사용하면 "누구의 데이터인가"를 화면이 매번
   확인해야 하고, 로그아웃 순간 남의 프로필이 사라진다.
2. **수명이 다르다.** family는 인자마다 provider를 새로 만들기 때문에
   `autoDispose` 없이 쓰면 방문한 사용자 수만큼 캐시가 무한히 쌓인다.
3. **노출 범위가 다르다.** 아래 §3.1 참고.

### 3.1 뱃지 provider 분기 — 갈라지는 지점은 리포지토리가 아니라 그 위

`fetchUserBadges`는 본인/타인이 같다. 갈라지는 건 그 위 조합 단계다:

- **본인**: `badgeProgressListProvider` = 카탈로그 + 획득 + `GamificationStats`
  → 미획득 뱃지와 진행률까지 계산.
- **타인**: `userBadgesByIdProvider`의 목록 **그 자체가 최종 결과**.
  진행률을 만들 근거 데이터(`GamificationStats`)를 애초에 얻을 수 없다 —
  그 사용자의 `runs`를 읽을 수 없기 때문이다. 억지로 카탈로그와 합쳐
  "미획득" 회색 아이콘을 그리면 남의 미달성을 전시하는 셈이라 UX상으로도 틀리다.

즉 **본인 갤러리(`badgeProgressListProvider`)에는 손대지 않았다** — 회귀 없음.

### 3.2 노출하지 않기로 한 것 (provider를 만들지 않은 것)

- **최근 러닝 목록**: `runs` RLS를 손대지 않기로 확정. 타인 러닝 provider를
  추가하면 RLS가 빈 목록을 돌려주므로 화면에 **"기록 없음"이라는 거짓말**이
  뜬다. 파일 주석에 금지 사유를 남겨두었다.

### 3.3 본인 id로 호출된 경우

`userProfileProvider(myId)`도 정상 동작한다(같은 `profiles` 행). 다만 화면은
본인 프로필 라우트로 보내는 편이 낫다 — 편집 진입점과 미획득 뱃지가 있는
쪽이 본인에게 더 유용하다. 라우팅 판단은 UI 담당.

## 4. backend와의 정합 (병행 작업분 대조 완료)

backend가 마이그레이션 53/54/55를 이미 작성했다. 내 모델·provider와 대조한 결과:

| # | 항목 | 상태 |
|---|---|---|
| B-1 | `profiles.weekly_goal_km` (53) | **정합.** `double precision` nullable, CHECK `> 0 and <= 500`. Dart는 `double?`이라 그대로 맞는다. 타입이 `numeric`이 아닌 이유(`weight_kg`/`height_cm`와 통일, PostgREST 정밀도 표현)와 상한 500의 근거가 마이그레이션 주석에 있다. TRD §4.1 행을 이 실제 타입으로 갱신했다 |
| B-2 | 가드 트리거 | **조치 불필요.** 블랙리스트 방식이라 컬럼 추가만으로 편집이 열린다(§2.2) |
| B-3 | `user_badges_select_public` (55) | **정합.** 술어가 `verified and not revoked`로, 내가 가정한 `revoked = false`보다 한 칸 보수적이다. `evaluate_badges`가 항상 `verified=true`로 발급하므로 현재 결과는 동일하고, "재검증 대기" 상태가 생겨도 타인에게 새지 않는다 — 더 나은 선택이라 그대로 수용 |
| B-4 | `avatars` Storage 버킷 (54) | 모델 변경 없음(`profiles.avatar_url` 기존 컬럼) |
| B-5 | `season_histories_select_visible` | 기존 정책 그대로. `bestTierOf`가 `isVoided`를 한 번 더 거르므로 어느 쪽이든 안전 |

### 확인 완료 — 본인 갤러리 회귀 없음

마이그레이션 55는 `user_badges_select_own`을 **대체하지 않고 병렬 추가**한다.
Postgres의 PERMISSIVE 정책은 OR로 합쳐지므로 본인은 여전히 `revoked = true`
행까지 보고(회수 사실을 화면에 표시해야 한다), 클라이언트
`fetchUserBadges`가 `revoked=false`를 다시 걸러 소비하는 현행 동작 그대로다.
`badgeProgressListProvider`도 손대지 않았다.

### 남는 위험 — UI/QA가 알아야 할 것

마이그레이션 55 주석이 짚은 대로, `user_badges`는 realtime publication에
들어 있어 이 정책이 붙는 순간부터 **타인의 뱃지 발급 이벤트도 구독자에게
도달**한다. 현재는 `watchUnseenBadges()`의
`PostgresChangeFilter(eq, 'user_id', userId)`가 막아 주지만, 지금까지 "덤"이던
그 필터가 이제 **유일한 방어선**이다. 타인 프로필 화면에서 뱃지를 realtime으로
구독하지 말 것 — 신설한 `userBadgesByIdProvider`는 의도적으로 1회성
`FutureProvider`이며, 여기에 realtime을 붙이면 남이 뱃지를 딸 때마다
재조회가 돈다.
