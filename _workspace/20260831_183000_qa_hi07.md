### P-3. 가드의 값 수렴 (정적 리뷰 PASS)

```
new := old  →  new.title/new.note 재적용  →  new.updated_at := now()

→ avg_pace_sec_per_km 재계산 → validate_run → compute_run_xp
```

되돌리기가 **파생값 재계산보다 앞서므로** 페이스·`is_flagged`·`awarded_xp`가 전부 `old`의 원본 입력을 근거로 계산된다 → 최초 업로드와 동일 값으로 수렴. 편집 UPDATE가 티어·랭킹·뱃지·XP를 흔들지 않는다. **회귀 검증 항목 5는 논리적으로 PASS**(실행 확인은 §4).

### P-4. INSERT 경로 무영향 (PASS)
화이트리스트 되돌리기 블록은 `if tg_op = 'INSERT' ... else` 의 **else 분기 안**에 있다. INSERT는 `new.created_at := coalesce(new.created_at, now())`만 타고 그 뒤 공통 정규화·파생값 계산으로 빠진다. 신규 업로드 경로 변화 없음(단, INSERT에도 title/note 정규화가 새로 적용된다 — 의도된 변화).

### P-5. 멱등 재적용 안전 (PASS)
`create or replace function` · `drop constraint if exists` → `add constraint` · `drop policy if exists` · 사전 절단 `update ... where char_length(...) > N`(2회차엔 0행). 전부 재실행 안전.

### P-6. `runs_delete_own` 제거가 폐기 흐름을 안 깨뜨린다 (PASS)
`LocalRunRepository.delete()`(`local_run_repository.dart:291-293`)가 **서버 DELETE 호출 자체를 제거**했다 — drift 행만 지운다. 호출부 두 곳(`tracking_providers.dart:167` `TrackingController.discard()`, `tracking_page.dart:1223` 미완결 배너 "버리기")은 이제 네트워크를 아예 타지 않으므로 정책 유무와 무관하다. 백엔드 메모가 근거로 든 "정책만 내리면 0행·무에러"는 여전히 참이지만, 클라이언트 변경으로 **모트 포인트**가 됐다. `.delete(` 전수 조사 결과 완료 기록을 지우는 호출부는 없다.

### P-7. 로컬 drift 부분 갱신 (PASS)
`_applyMeta`(`local_run_repository.dart:259-281`)는 `summaryJson`을 **읽어서 title·note·updated_at만 겹쳐 쓰고** 다시 넣는다.
- `samplesJson` 미변경 → 샘플 훼손·재직렬화 없음.

- 앱 재시작 후 `runRecordFromRow`(`local_run_database.dart:95-103`)가 같은 `summaryJson`을 파싱하므로 **값 유지 PASS**.

### P-8. 목록·상세 갱신 경로 (PASS)

## 2. CONFIRMED — 코드로 확인된 문제

### C-1. 오프라인에서 **미업로드 러닝**의 제목·메모 편집이 실패한다 · 책임: mobile(ui)
**파일:라인** `lib/features/tracking/data/local_run_repository.dart:229-244`

```dart
final confirmed = await guardSupabase(
  () => _client.from(_table).update(...).eq('id', id).select(_metaColumns).maybeSingle(),
);
final meta = confirmed == null ? RunMeta.normalized(...) : RunMeta.fromServer(confirmed);
```

로컬 전용 편집 경로는 **"요청이 성공했는데 0행"일 때만** 도달한다. 네트워크가 끊겨 있으면 `guardSupabase`가 `Failure.network`를 던지므로(`supabase_error.dart:39-45`) `_applyMeta`가 아예 호출되지 않고, 시트는 "저장하지 못했어요"만 띄운다.

**실패 시나리오** — 지하 주차장에서 러닝 종료 → `save()`가 로컬에 `pending`으로 저장하고 업로드 실패 → 사용자가 상세에서 "오늘 컨디션 최악" 메모를 씀 → **저장 불가.** 그런데 이 러닝은 **서버에 행이 아예 없으므로** 로컬 편집만으로 완전히 옳고, `syncPending()`이 갱신된 `summaryJson`을 그대로 실어 올린다(`_remotePayload`는 title/note를 제거하지 않는다). 즉 오프라인 우선 아키텍처가 정확히 겨냥한 국면에서 **불필요하게 막힌다.** UI 메모 §5-2가 "오프라인 편집 큐 없음"을 알려진 한계로 적었으나, 그 서술은 *이미 서버에 올라간* 기록에 대한 것이고 이 케이스는 큐 없이 해결된다.

**수정 제안** — `updateMeta` 진입 시 로컬 행의 `sync_status`를 먼저 읽고, `synced`가 아니면 네트워크를 타지 않고(또는 best-effort로 시도하되 실패를 삼키고) `RunMeta.normalized`로 로컬 확정 후 반환한다.

### C-2. `confirmed == null`이 "미업로드"와 "서버가 행을 못 찾음"을 구분하지 못한다 · 책임: mobile(ui)
**파일:라인** `local_run_repository.dart:238-240`

`update ... eq(id)`가 0행을 돌려주는 경우는 두 가지다 — ① 아직 업로드되지 않음, ② 서버에 행이 없거나 RLS(`runs_select_own`/`runs_update_own`)가 매칭에 실패함. 지금 코드는 둘 다 "로컬 전용 편집"으로 처리한다. ②에 해당하면 로컬만 바뀌고 `sync_status`는 `synced`로 남아 `syncPending()`이 재전송하지 않으므로 **영구 divergence**가 생기는데 사용자에겐 성공으로 보인다.

현재 UI 동선으로 ②에 닿기는 어렵다(자기 러닝만 상세 진입 가능). 그래도 판정 근거를 응답이 아니라 **로컬 `sync_status`**로 옮기면 C-1과 함께 한 번에 해소된다.

### C-3. 길이 상한의 **계수 단위**가 클라이언트와 서버에서 다르다 · 책임: ui
**파일:라인** `run_meta_edit_sheet.dart:139,148`(`maxLength:`) vs `run_repository.dart:109-116`(`normalizeRunMetaField`) vs 마이그레이션 51-1/51-2(`char_length` / `left`)

| 지점 | 계수 단위 |
|---|---|
| `TextField(maxLength:)` → `LengthLimitingTextInputFormatter` | **grapheme cluster**(characters 패키지) |
| `normalizeRunMetaField`(`runes.take(maxLength)`) | **코드포인트** |
| Postgres `left()` / `char_length()` | **코드포인트** |

`👨‍👩‍👧‍👦`(ZWJ 포함 7 코드포인트, 1 grapheme)가 섞이면 UI는 60"자"까지 통과시키지만 서버는 60 **코드포인트**에서 자른다 → 이모지가 반토막 난 문자열이 확정값으로 되돌아온다. 400은 아니다(가드가 CHECK보다 먼저 절단하므로 백스톱이 터지지 않는다) — **조용한 데이터 손상**이다.

주석(`run_repository.dart:88-90`)이 "코드 유닛이 아니라 룬 단위"라며 이 문제를 절반만 인식했다 — UTF-16 코드 유닛과 룬은 맞췄지만 **grapheme과 룬은 여전히 어긋난다.**

**수정 제안** — `maxLength` 대신 룬 기준 커스텀 `TextInputFormatter`를 쓰거나, `maxLengthEnforcement: none` + 카운터만 표시하고 서버 확정값을 신뢰한다. 어느 쪽이든 UI/서버/`normalizeRunMetaField`가 같은 단위여야 한다.

### C-4. HI-07로 붙인 제목이 **상세 화면 말고는 어디에도 표시되지 않는다** · 책임: ui/문서
전수 조사 결과 `title`을 그리는 곳은 `run_detail_page.dart:210-213` 하나뿐이다.
- `lib/features/history/presentation/widgets/run_tile.dart` — `title` 참조 **0건**
- `lib/features/sharing/presentation/share_card_sheet.dart:142` — `title: const Text('공유하기')`(시트 헤더). 러닝 제목은 카드에 없다.

그런데 60자 상한의 근거는 **"목록 카드/공유 카드에서 줄바꿈 없이 읽히는 한 줄 제목"**이다(마이그레이션 51-1 주석, TRD §4.4, 백엔드 메모 §2.6). 근거가 참조하는 표면이 존재하지 않는다.

부수 결론: **회귀 검증 항목 "run_tile·공유 카드가 긴 제목/null 메모에서 깨지지 않는가"는 깨질 위젯 자체가 없어 자동 PASS**이며, UI 메모 §5-3의 "긴 제목의 목록/공유 카드 렌더 미검증"은 **검증 대상이 없다**. 실기기 확인 대기 항목에서 내려도 된다.

**조치** — ① 목록 타일/공유 카드 제목 노출을 별도 과제로 올리거나, ② 60자의 근거 문구를 현실에 맞게 정정. 사용자가 붙인 제목이 아무 데도 안 보이면 HI-07의 동기 자체가 약해지므로 ①을 권한다.

### C-5. 마이그레이션 51-1의 **사전 절단 UPDATE가 AFTER 트리거 4종을 전부 깨운다** · 책임: backend
**파일** 마이그레이션 51-1 (`update public.runs set title = left(title, 60) where ...`, `note` 동일)

`runs_01_recompute_stats` · `runs_02_challenge_progress` · `runs_03_evaluate_badges` · `runs_04_notifications`은 전부 `after insert or update ... for each row`이고 **`WHEN` 절이 없다**(13:234-244, 45:350-353). 이 UPDATE는 `is_server_write()`를 켜지 않으므로 매칭되는 행마다 `recompute_season_tier` + `recompute_challenge_progress` + `evaluate_badges`(미획득 뱃지 전량 재평가) + 알림 인큐가 돈다.

중복 푸시는 `unique (user_id, dedupe_key)` + `on conflict do nothing`(44:116, 44:553)이 막는다 — **알림 폭탄은 없다.** 다만 마이그레이션이 임의 사용자의 집계를 대량 재계산하는 것은 의도가 아니다.

현재 title/note를 입력할 UI 경로가 이번 작업 전까지 없었으므로 매칭 0행일 가능성이 높다. **적용 전에 확인할 것:**

```sql
select count(*) from public.runs
 where (title is not null and char_length(title) > 60)
    or (note  is not null and char_length(note)  > 500);
```

0이 아니면 절단 UPDATE 앞뒤로 `set_config('runnit.server_write','on',true)` / `'off'`를 감싸는 것을 권한다.

## 3. PLAUSIBLE — 확률·영향이 낮거나 실행 검증이 필요한 항목

### L-1. 제목 한 줄 편집마다 전체 재집계 체인이 돈다 · 책임: backend
C-5와 같은 원인(트리거에 `WHEN` 절 없음)이 **평시 편집에도** 적용된다. 메모 한 줄 수정 UPDATE 하나가 프로필 캐시 재계산 → 챌린지 진척 재계산 → **미획득 뱃지 전량 재평가** → 알림 트리거를 유발한다. 결과는 멱등이라 값은 흔들리지 않지만(P-3), 편집이 흔한 동작이 되면 비용이 무시하기 어렵다.

개선안 — `runs_01`~`runs_03`에 다음 형태의 `WHEN` 절 추가:

```sql
when (tg_op <> 'UPDATE'
   or old.distance_meters is distinct from new.distance_meters
   or old.status          is distinct from new.status
   or old.is_flagged      is distinct from new.is_flagged
   or old.awarded_xp      is distinct from new.awarded_xp
   or old.started_at      is distinct from new.started_at
   or old.activity_type   is distinct from new.activity_type)
```

(단, `WHEN`은 화이트리스트를 다시 열거형으로 만드는 셈이라 51-2가 피하려 한 함정과 같은 성질이 있다 — "집계에 영향을 주는 컬럼"의 열거이므로 51-2의 컬럼 화이트리스트와는 축이 다르지만, 컬럼 추가 시 갱신 의무가 생긴다는 점은 같다. 트레이드오프를 backend가 판단할 것.)

### L-2. 편집이 뱃지를 "그 러닝이 딴 것"으로 오귀속하고, 알림이 삼켜질 수 있다 · 책임: backend
`trg_runs_evaluate_badges`는 `evaluate_badges(new.user_id, new.id)`를 부른다(13:214-232). 편집 시점에 시간 경과·다른 상태 변화로 조건이 새로 충족된 뱃지가 있으면 `source_run_id = 편집한(오래된) 러닝`으로 지급된다. 게다가 NT-06의 dedupe 키가 `'badge_level:run:' || new.id`(45:335)라, 그 러닝으로 이미 성취 푸시가 나간 적이 있으면 **새 뱃지 알림이 조용히 삼켜진다**.

재현 확률은 낮다(같은 사용자·같은 러닝 id에 대해 뒤늦게 조건이 충족되는 뱃지가 있어야 함). L-1의 `WHEN` 절로 함께 해소된다.

### L-3. `recording`/`paused` 행은 화이트리스트 밖이다 · 책임: backend
51-2의 잠금 조건은 `old.status in ('completed','discarded')`다. 향후 체크포인트 업로드를 위해 의도적으로 열어 둔 예외라고 주석이 밝히고 있으나, 그 경로가 생기는 순간 **"`recording`으로 INSERT → 자유 UPDATE로 원본 조작 → `completed`로 확정"**이 열린다. 현재는 `save()`가 완료 기록만 올리므로(`local_run_repository.dart:81-88`) 서버 행이 항상 터미널 상태라 **미도달 = cannot reproduce**. 체크포인트 업로드를 도입하는 사람이 이 파일을 함께 고쳐야 한다는 경고를 51-2 주석에 한 줄 추가할 것을 권한다.

## 4. SQL 미적용 — 원격 적용 후 확인해야 할 항목

이 환경에 `psql`·`docker`가 없어 **파싱·실행 검증을 하지 못했다.** 아래는 정적 리뷰로 대체할 수 없다.

1. `new := old` **행 통째 대입**이 이 스키마의 `runs`(enum 배열 `device_vendors`, `jsonb samples`, 다수의 `timestamptz`)에서 실제로 파싱·실행되는가. → plpgsql의 표준 idiom이지만 실행 확인 필요.
2. 완료 러닝에 `distance_meters` UPDATE 시도 → 값 불변 + **200 응답**(4xx 아님).
3. 같은 행 `title`/`note` UPDATE → 반영, `updated_at` 갱신, `avg_pace_sec_per_km`·`awarded_xp`·`is_flagged` **불변**(P-3의 실행 확인).
4. 61자 title → 60자 절단 저장, CHECK 위반 400이 **아님**. **ZWJ 이모지 혼입 시 절단 위치**(C-3의 실측).
5. 같은 payload 재 upsert(오프라인 멱등) → `is_flagged`/`awarded_xp` 동일, 에러 없음.
6. 완료 러닝 DELETE → 0행, 에러 없음(클라이언트가 더 이상 호출하지 않지만 정책 제거 자체의 확인).
7. C-5의 사전 절단 대상 행 수 사전 조회.
8. `get_advisors`(security/performance) 재확인.
